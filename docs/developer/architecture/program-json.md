# Program JSON 6.1.0

The separate backend [DOE reference catalog](../research/reference-program-contract.md#source-packet) preserves source identities and declared departures. Its packet format is not atlas program JSON; this component's schema and illustrative defaults are unchanged.

> **Status:** Provisional (ADR-018 and [ADR-027](../decisions/ADR-027-atlas-release-2-0-0-contracts.md), realisation pending the owner's reading) · **Since:** version 1.2.0 (D-126); program JSON 5.4.0 of atlas release 2.0.0 since D-172, of release 2.1.0 since version 1.6.0 (D-198), and of release 2.2.0 and later labels since version 1.7.0 (D-205); program JSON 6.0.0 of atlas release 2.3.0 since version 1.9.0, and 5.4.0 no longer (D-239, [ADR-038](../decisions/ADR-038-atlas-release-2-3-0-contracts.md)); program JSON 6.1.0 of atlas release 2.4.0 since version 1.10.0, and 6.0.0 no longer (D-253, [ADR-040](../decisions/ADR-040-atlas-release-2-4-0-and-the-unoccupied-lighting-cap.md)); the editor window and the LF checksum since D-128, on `main` since D-207 · **Component:** *Program JSON* (`PJson`), panel *1 Program*, GUID `abb0aeb9-5a9f-40ff-b3a1-bb125cfb675c` · **Code:** `Lod.ProgramJson` (`src/Lod.ProgramJson/`) · **Design notes:** [2026-10-07-program-json.md](../plans/2026-10-07-program-json.md), [2026-10-28-atlas-release-2-0-0.md](../plans/2026-10-28-atlas-release-2-0-0.md)

## Purpose

The Energy Archetype Atlas publishes a program as *program JSON*: one JSON object with the program's loads, its controls, and every schedule they use. Atlas release 2.4.0 (a delta on 2.3.0 with the PNNL prototype corrections of the review's round 2: the unoccupied lighting cap, the PNNL office lighting power, the 90.1 elevators and kitchen reach-ins; the atlas's ADR 0060 to ADR 0062; D-253) exports **program JSON 6.1.0**, which is 6.0.0 with the optional `lighting_controls.unoccupied_lighting_cap` (releases 2.0.0 to 2.2.0 exported 5.4.0 and release 2.3.0 6.0.0, which BEMGen reads no more), in two versions: `source`, the actual values only, with what the source does not record left `null`, and `filled`, with the atlas's fillings and approved defaults applied (policy `atlas-program-defaults-2.0.0`) and the hot water as draw-only water heating. IECC programs and code-prototype dwellings export the source version only. *Program JSON* turns the text of either version into a ready-to-use [program preset](../research/program-presets.md#7-atlas-programs-program-json-d-126): the preset goes into any preset input of a plan generator, into *Any Program Preset*, or into *Mix Programs*, and is converted by *Convert2BEM* and *Convert2IDF* like any other.

The solve reads only the JSON **text**: no file path and no network. The component's atlas window (below, D-208) uses the network after a click, from the atlas site only, and stores the text it downloads. A program JSON 5.4.0 of releases 2.0.0 to 2.2.0 or 6.0.0 of release 2.3.0 is refused with the advice to take it again from release 2.4.0, and the refusal names the program's release 2.4.0 ID through the atlas's ID maps, embedded byte for byte (`AtlasIdMap`, D-240, D-254): a 2.2.0 ID through `id-map-2.3.0.json` and then `id-map-2.4.0.json`, a 2.3.0 ID through `id-map-2.4.0.json`; the retired program JSON 2.0.0 (D-126) is refused too. The embedded schema is the atlas's 6.1.0 schema, revision 1 (atlas `7c543f5d`, with its `$comment` revision marker), whose `source.release` is the pattern `^atlas-release-\d+\.\d+\.\d+$`. The contract's schema, twelve release exports, and the recorded atlas site's three store files (`Fixtures/site/`, D-208) are the only atlas program files in the repository; `tests/Lod.ProgramJson.Tests/Fixtures/README.md` gives their origin and `manifest.json` their SHA-256.

`Lod.ProgramJson` is a plain library (`net7.0`, like the plugin) that depends on `Lod.Core` and the JSON Schema library; it never references RhinoCommon or Grasshopper (AGENTS.md). The component is a thin adaptor (GLOBAL.md architecture rule 3).

## The contract

The schema is `program-json-v6.schema.json` (Draft 2020-12), one `oneOf` of a `source` and a `filled` branch, embedded byte for byte in `src/Lod.ProgramJson/Schemas/`. The members BEMGen reads:

## How a JSON becomes a preset

`ProgramJsonImporter.Import(json, options)` runs these steps in order; each stops the read when it finds an error, and every diagnostic carries the JSON Pointer (RFC 6901) of the node it concerns, or the name of the input for an option.

1. **Strict parse** (`StrictJson`): UTF-8 JSON, no byte-order mark, no non-finite number, no repeated member name (`ProgramJsonDuplicateKey`), at most 64 MiB and nesting depth 64 (`ProgramJsonLimits`). The checksum (`Json.Sha256`) is the SHA-256 of the atlas's canonical JSON of the document (D-226, `CanonicalJson`, atlas ADR 0057): members sorted by code point, no whitespace between tokens, strings in UTF-8 with only quote, backslash, and control characters escaped, numbers as Python's `json` writes them (an integer as written, any other number as `repr` of its double: `100.0`, `1e-05`), no trailing newline. It is the site's `json_sha256`: the site's store text, the release's pretty-printed file, a CR LF panel (Grasshopper stores text with CR LF), and a re-indented copy of one JSON have one checksum, which `python -m scripts.site_store FILE` in the atlas prints. It is not the file's own SHA-256: `Fixtures/atlas/manifest.json` pins the fixtures' bytes, as written on Windows with CR LF, while the reader gives the canonical checksum. D-128 and D-207 hashed the text with LF line endings, which differed between the site's text and the release's file.
2. **Version:** `kind` must be `program` and `schema_version` `6.1.0` (`ProgramJsonVersionNotSupported` otherwise, before the schema; the message names the retired 2.0.0 when the text has an `export_mode`).
3. **Schema:** validation against the embedded schema (JsonSchema.Net, Draft 2020-12). Every violation is reported with its instance path and keyword; the root `oneOf` reports both branches, so one wrong value can give several lines.
4. **Resolution:** the loads are selected for the **climate zone** and the **construction context** (below), then the contract's checks and the **expansion** of every referenced schedule.
5. **Mapping** to a `ProgramPreset` and the **overrides** of the component's inputs.

A heat fraction a load type does not have is refused by the 5.4 schema itself.

## Climate zone and construction context

- **Climate zone** (*Climate Zone* input, `ProgramJsonImportOptions.ClimateZone`, the contract's `^[0-8][A-C]$`, upper-cased): `value_by_climate`, `schedule_id_by_climate`, `fenestration.value_by_climate`, and `lighting_controls.daylighting_by_climate` take the zone's entry when there is one, otherwise the general value. Without a zone the general value is used, with `ProgramJsonClimateZoneNotGiven` when the document has entries; the document lists what was not resolved (`ProgramJsonDocument.UnresolvedClimate`), and the preset's source records it as `ClimateZone.Unresolved` (`<program ID>: the <what> (<zones>) differ by climate zone`), so that *Convert2IDF* refuses the program (D-213, [convert2idf.md](convert2idf.md#weather)). A load taken from `value_by_climate` is marked in the document (`ProgramJsonLoad.ValueByClimate`), and the zone is recorded as `ClimateZone` in the preset's source.
- **Construction context** (*Context* input, `key=value` items, `ProgramJsonImportOptions.Context`): a load with `applies_with` (such as the IECC dwellings' `{"foundation": ["crawlspace", "slab", "unheatedbsmt"]}`) is instantiated when every condition's key has a context value among its values, and left out (listed in *Left Out*) otherwise. A key without a context value is `ProgramJsonContextRequired`: keeping both variants would double the load and dropping both would lose it. The context is recorded as `Context`.

## Expanding schedules

Unchanged from D-126: every referenced schedule becomes 8760 hourly values on the calendar of the *Year* input (default 2007, whose 1 January is a Monday) and the *Holidays* input; a leap year is an error. Rulesets use `last_specific_match_else_last_default` in array order; a holiday matches `Hol` only, else the last `Default` rule; `02-29` boundaries move to 1 March or 28 February with a warning; design days (`WntrDsn`, `SmrDsn`) are checked and not used, each schedule with design-day rules gets one *Left Out* line, and the IDF gives design days the Sunday profile. The filled release-2.0.0 schedules resolve holidays as Sundays where the source had no holiday rule (the atlas's `accepted-holiday-sunday`, recorded in `metadata.resolutions`), so the D-126 gap 2 (holidays falling to the prepended `Default` rule) no longer shows for the medium office's lighting and equipment.

### Daylighting (atlas handoff item 1)

The daylighting fractions of release 2.0.0 are plain program values (atlas user decision L-1; the 1.5.0/1.6.0 flag `geometry_dependent` is gone and is not read). They are applied as given and never recomputed from BEMGen's geometry:

- `status: known` with a `daylighting` block (or the climate zone's `daylighting_by_climate` entry) becomes `DaylightingControls`: `controlled_lighting_fraction`, `illuminance_setpoint_lux`, `control_type` (`continuous`, `stepped`, `continuous_off`), `method` (`split_flux`, `delight`), `minimum_input_power_fraction`, `minimum_light_output_fraction`, `stepped_control_steps`; `availability` is `all_days_except_design_days`.
- `daylighting: null` with `status: known` is a source zero, and `status: unknown` is not recorded: neither gives controls. A program without `lighting_controls` (a dwelling) has none.
- `controlled_floor_fraction`, `controlled_zones`, and `zones` are provenance, recorded in the `Daylighting` source parameter, never an instruction to split zones.
- A mix (*Mix Programs*) and a merged zone take each member's controls by the aggregation rule of [program-presets.md](../research/program-presets.md#7-atlas-programs-program-json-d-126): the controlled lighting power is conserved.
- **Code rule (D-233, ADR-037).** The controls carry the `DaylightingCodeRule` that places them when *Convert2IDF*'s Daylighting option is on: the program's template (`source.template`; 90.1-2010, or 90.1-2013, 2016, and 2019, which share openstudio-standards' rule, and since D-248 the IECC editions 2006 to 2021, which take the 90.1-2019 rule by the owner's decision; any other template has none), its openstudio-standards building and space type from the evidence entry whose locator is `space_types <building type> / <space type>` (for the retail and apartment exceptions), the `standards_rule`'s `primary_sidelit_nongeometry_fraction` and `secondary_sidelit_nongeometry_fraction` (`ProgramJsonStandardsRule`; applied only for Office `WholeBuilding` space types, as openstudio-standards applies them, otherwise noted as not applied), and the import's climate zone. An IECC program has no `space_types` evidence and no `standards_rule` (D-248): its space type is its `name` before `_<source.building_type>` (`WholeBuilding - Sm Office_SmallOffice`), its building type `standards_building_type`, and its office whole-building fractions openstudio-standards 90.1-2019's (`NinetyOneTwentyNineteenSpaceTypes`, `ashrae_90_1_2019.spc_typ.json` at `c8c1b9eb`). `daylighting_appropriate: false` gives no rule. The preset's source records the rule as `DaylightingRule` (or `none: …` with the reason).
- By default the controls are source data and provenance: *Convert2IDF* writes them only when its Daylighting input is on (D-233), placed by the code rule on BEMGen's own windows and skylights; with it off, the default, daylight dimming is held fixed as part of the lighting load (D-174's rule; [convert2idf.md](convert2idf.md#daylighting-d-172-d-174)). `controlled_lighting_fraction` is never what is written. The *Left Out* output says so. *Convert2BEM* does not output the controls.

### Glazing

The preset's WWR per orientation and skylight ratio come, in this order, from: *WWR North/East/South/West* (`WindowToWallRatios`); the glazing fixture's entry (`ProgramJsonImportOptions.Glazing`, the stand-in of DOE geometry note A2, kept for its tests); *WWR* when connected; the JSON's `fenestration` for the climate zone, a `null` direction taking 0 (no exterior wall there, so no window), recorded as `… (the JSON's fenestration, program_zone_surfaces[, climate zone z], evidence e; …)`; and 0.4 (`default, not from the JSON`). The skylight ratio likewise ends with the JSON's `roof`, then 0. The JSON's ratios are on the true outdoor wall of the program's source zones; a generator reproduces glazed area per orientation and program (DOE geometry note S5).

## Overrides

The inputs after *JSON* complete or override the JSON. Unset, the JSON's value (or the stated default) is used.

| Input | Default | Effect |
| --- | --- | --- |
| *Name* | the JSON's `name` | the preset name; recorded as an override |
| *Space Type* | unset: an any-program preset | the space type the preset applies to |
| *WWR* | unset: the JSON's `fenestration`, else 0.4 | the window-to-wall ratio in [0, 1) on all four orientations |
| *Year*, *Holidays* | 2007, none | the calendar |
| *Loads* | none | each load replaces every JSON load of its type and end use (ignoring case), whatever its basis, or is added; two of one type, end use, and basis are an error |
| *Heating On*, *Cooling On* | the JSON's switches (not recorded: off) | switch each side |
| *Heating Setpoint*, *Cooling Setpoint* | the JSON's schedules | replace the JSON's; used only when that side is on |
| *Activity*, *People Radiant*, *People Sensible* | the JSON's (not recorded: BEMGen's defaults) | the people properties |
| *WWR North* … *WWR West*, *Skylight Ratio* | unset | glazing per orientation and skylight ratio (DOE geometry note S5) |
| *Climate Zone* | unset: the general values, which *Convert2IDF* refuses for a program with values by climate (D-213) | the model's ASHRAE climate zone, such as `5B` (D-172) |
| *Context* | unset | `key=value` items of the construction context, such as `foundation=slab` (D-172) |

Outputs: *Preset*; *Source*; *Assumptions*, the JSON's `metadata.resolutions` and then its `metadata.absent_demands`, one compact JSON text each; *Overrides*; and *Left Out*, every part of the document the program does not hold. Errors and warnings are runtime messages.

## The editor window

Since D-128 the component has a strip at its bottom, *Edit JSON…* (*Edit JSON… (wired)* when *JSON* has a wire). A double-click on the strip opens a window, an Eto dialog modal over the Grasshopper editor, with one multi-line monospaced text field prefilled with the *JSON* input's stored text, and *OK* and *Cancel* (also Esc). It is an additional way to give the *JSON* input its value; every other input, output, and behaviour of the component is unchanged.

- **OK** runs `ProgramJsonTextCheck.Check` (`src/Lod.ProgramJson/ProgramJsonTextCheck.cs`):
  - empty or white-space text **clears** the stored text;
  - text the reader accepts (strict parsing, the version, the schema, the resolution, the contract's checks, and the expansion of every schedule) is **stored**, its warnings appearing on the component when it solves;
  - text the reader rejects is **not stored**: the window stays open and lists the errors below the text field, one per line (`Error <code> [<JSON Pointer>]: <message>`).

  The check expands the schedules on the component's *Year* and *Holidays* when each holds what one solution reads (one year, one list) and they make a valid calendar, else on 2007 without holidays. It resolves the loads on the component's *Climate Zone* when that holds one text, and on its *Context* when every item is a `key=value` pair with no key repeated, else on none (D-207), so a JSON whose loads need a construction context is accepted when the component gives one, as the solve accepts it. A wired input is read from its last solution, an unwired one from its stored values. The overrides are not part of it; the solve checks them, as before.
- **Storing** (`ProgramJsonComponent.SetJsonText`) replaces the *JSON* input's persistent data with the text exactly as given, records one undo event (*Edit JSON*), and expires the *JSON* input, which expires the component downstream of it, so the component collects the new text when the solution runs. Expiring only the component would keep the input's old collected data, and the component would report that *JSON* failed to collect data. When *JSON* stores several texts (*Set Multiple Text*), the window shows the first and says that OK replaces all of them with its one text. The stored text is saved in the definition like any internalised value; Grasshopper gives it back with CR LF line endings, which the checksum ignores.
- **A wire wins.** As everywhere in Grasshopper, a wire into *JSON* takes precedence over the stored text, which is kept and used again when the wire is removed. The window then says so above the text field. *Clear values* on the input removes the stored text, as OK with an empty text field does.

The window cannot be shown in a headless Rhino, so `scripts/rhino-smoke/specs/program-json-editor.py` checks the layout of the strip and calls the two methods OK uses (`CheckJsonText`, `SetJsonText`); a person checks the window itself ([smoke test](../development/grasshopper-smoke-test.md#program-json-editor-window-checklist-d-128)).

## The atlas window (D-208)

The strip *Get from Atlas…*, above *Edit JSON…*, opens on a double-click a window with an address box, a web view of the Energy Archetype Atlas site, a choice of the **filled** (default) or **source** version, a status line, *Use this program*, and *Cancel*. It replaces the clipboard of D-129: BEMGen reads the page's **address**, not the page or the clipboard.

- **The site** is fixed: `AtlasSite.Root`, `https://energy-atlas.github.io/archetype-atlas/`. The window opens on its catalogue (`catalogue/`) and refuses any other address (scheme, host, port, or a path outside the root), from the address box, a link, or a link that opens a new window (which opens in the same view when it is on the site), with a status line naming it.
- **The index.** When the window opens, `AtlasSite.ReadIndexAsync` reads `site-manifest.json` and refuses an index marked `partial` (`AtlasSiteIndexPartial`) or of another shape (`AtlasSiteIndexInvalid`: a `release` other than `X.Y.Z`, a page that is not a path under the root ending in `/`, a store path other than `store/<sha256>.json.gz`, two programs on one page). The other keys of the index and of a program are ignored. The index is kept for the Rhino session while the site's cache time, 10 minutes, holds; a failed read is not kept.
- **A page's program.** `AtlasSiteIndex.ProgramForPage` gives the program whose `page` is the address's path below the root, as the server reads it (not decoded, with case; a trailing `index.html`, the query, and the fragment ignored). *Use this program* is enabled only then. Each program's page selects *Filled*, except a program the site publishes only as source (the IECC programs and the code-prototype dwellings, with the site's `filled_reason`), which selects *Source* and says why.
- ***Use this program*** runs `ProgramJsonComponent.PickFromAtlasAsync`: `AtlasSite.DownloadAsync` fetches the store file of the chosen version and refuses it unless the SHA-256 of its gzip bytes is the hash in its path (`AtlasSiteChecksumMismatch`), it decompresses to UTF-8 JSON of at most 64 MiB (`AtlasSiteProgramInvalid`), its `id` and `version` are the program and the version (`AtlasSiteProgramMismatch`), and its `source.release` is the index's (`AtlasSiteReleaseMismatch`); a filled version the site does not publish is `AtlasSiteVersionNotPublished`. Then the editor window's check (`CheckJsonText`, on the component's calendar, climate zone, and context) runs. When it stores the text, the window closes and `SetJsonText` stores it with one undo event; otherwise the status line names the program, the version, the release, and what failed.
- **The stored text** is the store file's content byte for byte, the site's canonical JSON (compact, no line breaks). *Source*'s `Json.Sha256` is its canonical checksum, the same as that of the pretty-printed file of the release zip `atlas-release-2.4.0.zip` (D-226). *Source* also names the store file, `Json.Store` (`<site root>store/<sha256>.json.gz (atlas site release 2.4.0)`): the component keeps the last pick's store path, release, and checksum (saved in the definition) and records it only while the *JSON*'s canonical checksum is the pick's, so an edited or rewired text with other content does not claim it. The DOE maps and the atlas mixes record each key's or member's store file the same way, against the checksum of its text as downloaded, kept in the stored text (the map's format 1.1.0; a map stored as 1.0.0 by 1.8.0 reads and records no store file). A map or mix stored from site release 2.3.0 or earlier holds program JSON 6.0.0 or 5.4.0 and that release's IDs, so the solve refuses it as a whole (`AtlasSiteStoredBeforeRelease`, D-240, D-254), naming each moved program's release 2.4.0 ID through `AtlasIdMap`; *Get from Atlas…* stores it again from the site's release.
- **Offline.** A refused connection, a timeout (30 s per request), and an HTTP error are messages on the status line (`AtlasSiteUnreachable`, `AtlasSiteTimedOut`, `AtlasSiteHttpError`), never exceptions. The solve never uses the network, so a stored program solves offline.
- **Rate limits and parallel downloads (D-225).** An answer of HTTP 429 or 5xx is asked for once more after a pause (2 s, or the server's `Retry-After` when longer, at most 10 s); a 429 after that is `AtlasSiteRateLimited`, whose message says the site's host limits this network's downloads and to wait a few minutes. One site fetches at most four store files at once (`AtlasSite.MaxConcurrentDownloads`), so the DOE maps and the atlas mixes queue their programs. Every handler of the atlas windows catches any other exception into the status line.
- **Code.** `Lod.ProgramJson.Site`: `AtlasSite`, `AtlasSiteIndex`, `AtlasProgramPicker` (the window's logic without the window), the transports `HttpAtlasSiteTransport` (the window's) and `FileAtlasSiteTransport` (recorded files, for the tests and the smoke check). The window is `ProgramJsonAtlasDialog`. Pasting stays possible through *Edit JSON…*.

The headless smoke check runs the window's two calls (`AtlasPageStatusAsync`, `PickFromAtlasAsync`, then `SetJsonText`) on the recorded site files of `tests/Lod.ProgramJson.Tests/Fixtures/site/`; a person checks the window itself ([smoke test](../development/grasshopper-smoke-test.md#atlas-window-checklist-d-208)).

## Atlas program maps and generation files (D-209)

Since the atlas's ADR 0052 the site's index gives each program its `folder`, `mode`, `space_type`, and `building_type`, and a top-level `folders` with each folder's sorted `programs` and its `generation` store file or `null` ([ADR-036](../decisions/ADR-036-atlas-program-maps.md)). `AtlasSiteIndex` reads them as `AtlasSiteProgram.Folder`, `Mode`, `SpaceType`, `BuildingType`, `AtlasSiteIndex.Folders` (`AtlasSiteFolder`, `AtlasStoreFile`), and `ReleaseManifestSha256`; a folder whose path is not its family, template, and building type, a folder that lists a program the index does not hold in that folder or lists one twice, a program whose folder does not list it, a `generation` other than a gzip store file whose `sha256` is the hash of its path, with positive sizes, or one of the four program fields not a text is a fault of the folders (`AtlasSiteIndex.FoldersFault`, `AtlasSiteIndexInvalid`): the index then reads with no folders and those fields `null`, so the atlas window of *Program JSON* still works, and everything that needs the folders refuses with the fault. An index without these fields reads with no folders and no fault.

- **Matching** (`AtlasSiteIndex.MatchKeys(folder, keys)`): a key matches the folder's one program of mode `source` whose `space_type` is the key, exactly. Department and general programs (the atlas's merged `*_Mixed` programs) are never candidates. The result gives each key's program or none, and the number of candidates (0 for a gap, more for an ambiguity).
- **The DOE *Programs* components** use it through `AtlasProgramMapPicker` (`OpenAsync`: the families that hold the prototype's folder, with their coverage; `PickAsync`: every matched key's program downloaded in parallel with `AtlasSite.DownloadAsync`, each given the program check, gathered into one `AtlasProgramMap`), and the solve imports the stored map offline with `AtlasProgramMapImporter`, which runs `ProgramJsonImporter.Import` per key ([doe-components.md](doe-components.md#atlas-program-maps-d-209)).
- **Generation files** (`AtlasSite.DownloadGenerationAsync(folder)`): the folder's `generation.json`, checked by the hash of its path, the decoded size the index gives, and a JSON object whose `programs` names every program of the folder; `AtlasSiteGenerationNotPublished` where the folder has none, `AtlasSiteFolderNotInIndex` for an unknown folder. `AtlasGenerationPicker` finds the folder of a program JSON's `id` for *Schedule Draw* ([schedule-draw.md](schedule-draw.md#generator-json-from-the-atlas-site-d-209)).

## Atlas mixes on Mix Programs (D-228)

The site index (site index schema 1.0.0, atlas ADR 0058) gives each folder's `compositions`: for each general and department mix, its members' release program IDs, `represented_area_m2`, and `weight` (the area share). `AtlasSiteIndex` reads them strictly (D-227): every member a source program of the folder, listed once, an area of at least 0, weights summing to 1 and equal to the area shares within `ToleranceSettings.AbsoluteFraction`, each mix of the folder with its composition and mode; a fault drops the compositions only (`CompositionsFault`), so the DOE maps and generation files keep working.

- **The window** (`MixAtlasDialog`, logic in `AtlasProgramMixPicker`) lists the folders with source programs by template and building type, and a folder's starting selections (`Starts`): each general mix, then each department mix, with their members ticked and their area shares as weights, and a free selection of every source program, unticked, with its share of the folder's general mixes where it is a member of one (the plenum of the medium office is in none, so it has no weight until one is typed). The user unticks members and edits weights; the table shows each normalised share.
- **OK** downloads every ticked member (filled by default, or source) with `AtlasSite.DownloadAsync` (at most four at once), checks each with `ProgramJsonTextCheck` on the component's *Climate Zone*, *Year*, *Holidays*, and *Context*, and mixes them with the stored weights as the solve does (the solve also applies the component's *Name*, *Space Type*, and *WWR*, which OK does not); only a mix that solve accepts is stored, as one text `bemgen-atlas-program-mix` 1.0.0 (the site, its release and manifest checksum, the folder, the starting selection, the version, and per member its program, space type, store path, represented area, weight, text, and the text's canonical checksum as downloaded), with one undo event. *Clear* removes it. The starting selection and the represented areas are taken from the index, never from the window. A wire into *Presets* takes precedence even when it delivers nothing (a warning says so); a definition saved before D-228 reopens with *Presets* and *Weights* made optional.
- **The solve** (`AtlasProgramMixImporter`) imports each member with `ProgramJsonImporter.Import` (an any-program preset named by its space type, `Json.Store` in its *Source*), checks that each text is the program and version it is stored as, and mixes them with `ProgramMix.Mix` (D-124) on the stored weights or the given *Weights*. The mix's *Source* records each member's name and weight (`Input.k`) and nests each member's own *Source*, so the plan's provenance names every atlas program, checksum, and store file.
- **Why BEMGen mixes the members** instead of taking the atlas's own `General_Mixed` program, which *Program JSON* also reads: members can be unticked and reweighted, and every member stays traceable. The two can differ where the atlas's mixing differs from D-124's.

### The unoccupied lighting cap (D-256, ADR-040)

Program JSON 6.1.0 records PNNL's per-zone EMS rule of the 90.1-2019 prototypes on 19 programs (the offices, both restaurants, both retail types, the warehouse; the atlas's ADR 0060 section 1): while the zone's occupant count (or, for the warehouse storages, the office's) is 0 and its lighting is at least 0.02 W/ft², the zone's general lights are set to 0.02 W/ft². The rule is read as recorded (`ProgramJsonLightingCap`, `ProgramJsonLightingCapRule`) and becomes `UnoccupiedLightingCap` on the program:

- `cap_W_m2` (0.21528, the cap's 0.09290304 m²/ft²) and `lighting_threshold_W_m2` (0.21505, the threshold's 0.093) as given; `condition` (`zone_occupant_count_zero`, or `other_zone_occupant_count_zero` with `condition_zone`), `calling_point`, `additional_lighting_when_capped_W_m2` (the strip mall's display lighting, 0), and `zone_conditions` (single source zones whose programs add a condition) are kept; `comparison`, `action`, `zones`, `controlled_zones`, and `source_values` are provenance.
- `rule: null` is a source zero (1,875 programs: 90.1-2007 and 2013, the other 90.1-2019 types, IECC, DOE Ref) and gives none; *Source*'s `LightingCap` gives its reason from `nulls`. An unknown block and a mix have no field: a mix takes its members' caps by the merge rule (below).
- *Source* records the rule as `LightingCap` (the source values, the SI values, the condition, the calling point, the zones, and the added conditions, not applied). *Left Out* says that *Convert2IDF* writes it only when its *Lighting Cap* input is on (off by default) and lists each source zone's added condition as not applied: BEMGen's zones are not the source's.
- A mix (*Mix Programs*) and a merged zone keep the cap only when every source carries the same rule, with a floor-area aggregation record; otherwise they have none, with the warning `LightingCapDiffers` (D-256), since capping the merged zone would cap the lighting of a source whose program does not.
- The release also corrects 11 office lighting powers to PNNL's (90.1-2019 medium office 6.889 → 6.664 W/m², the atlas's ADR 0060 section 2): read as any load.

## What is left out

- **Shared services**, **building services**, **water heating owned once per building**, **exterior lighting**: not in a zone program; listed in *Left Out*. Since release 2.4.0 the building services include the 90.1 elevators and kitchen reach-ins, each listed by its ID; the building-level exterior elevators of the 90.1 hospital, large hotel, and large office are in the folder's building-services export only, which BEMGen does not read, so no program names them (D-258).
- **Water heaters** (the `water_heating` stages): systems, not modelled at ideal-loads grade.
- **Hot-water zone gains** (`water_use_gains`): BEMGen writes water use without zone gains.
- **Humidity setpoints**: ideal loads control temperature only.
- **The source calendar's holiday rules**: give the year's holidays through *Holidays* (resolving the rules is open).
- **Design-day profiles**: checked, not used. **Leap years**: an error.
