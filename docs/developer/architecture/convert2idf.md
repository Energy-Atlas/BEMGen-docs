# Convert2IDF output

> **Status:** Provisional (ADR-010, realisation pending the owner's reading); program fields, single-sided thermostats, and the calendar-based run period since D-126 ([ADR-018](../decisions/ADR-018-program-json-and-extended-programs.md)); EnergyPlus 26.2, the weather file, the research outputs, the ground temperatures, and the site record since D-130 ([the stage note](../plans/2026-10-11-idf-out.md)) · **Since:** S6 (version 0.9.0, D-113) · **Component:** *Convert2IDF* (`2IDF`), panel *5 Convert*, GUID `56dd6611-90b2-4299-b53c-650652843a1a` · **Code:** `Lod.Export.Idf` (`src/Lod.Export/Idf/`)

## Purpose

*Convert2IDF* is the second converter of the pipeline (D-020). It writes an EnergyPlus 26.2 input file (IDF) from an `IGeneratedBuilding` and an envelope preset, as [ADR-010](../decisions/ADR-010-convert2idf.md) specifies, ready to simulate with the weather file it names (D-130, [the stage note](../plans/2026-10-11-idf-out.md)). The converter does not run EnergyPlus: a run is not a pipeline step. Correctness is checked by reading the file back (see [Tests](#tests)).

`Lod.Export` is a plain C# library (`netstandard2.0`) that depends only on `Lod.Core`, never on RhinoCommon or Grasshopper (AGENTS.md). Its tests (`tests/Lod.Export.Tests`) run with `dotnet test`.

## Interface

```csharp
Result<IdfDocument> result = new IdfWriter(ToleranceSettings.Default)
    .Write(building, ExampleEnvelopePresets.Example, new IdfOptions(new HeatTransferOptions(false, false)));
string idf = result.Value.ToText();
```

| Type | Role |
| --- | --- |
| `IdfWriter` | `Write(building, envelope, options)`: validates the building, then builds the document; returns `Result<IdfDocument>` with diagnostics. `Write(building, constructions, options)` takes a `ConstructionSet` instead (D-137, [Construction sets](#construction-sets)); an envelope preset is written as the set `ConstructionSet.FromEnvelope(envelope)`, which gives exactly the text the preset alone gave. |
| `IdfOptions` | `HeatTransfer` (`HeatTransferOptions`, D-069, both off by default), `OverrideValidation` (default `false`), `FirstDayOfYear` (weekday of 1 January of the schedules; unset by default, which takes it from the building's calendar, else Monday, as every example preset; a weekday given here must agree with the calendar, D-126), `Weather` (`IdfWeather?`, the weather file the IDF is written for, D-130; none by default). `IdfOptions.Default` has all defaults. |
| `IdfDocument` | `Header` (comment lines), `Objects` (typed objects in file order), `ToText()` (the IDF text with `\n` line ends). |
| `IIdfObject` and the `Idf…` records | One typed record per EnergyPlus class (`IdfZone`, `IdfBuildingSurface`, `IdfScheduleYear`, …), each giving its fields in EnergyPlus 26.2 order. |
| `IdfDefaults` | Every modelling default of the writer, in one place (table below). |
| `Convert2Idf` | `Run(building, envelope, options, file, weatherPath)`: the service behind the component. Reads the weather file when `weatherPath` is given (fully qualified, as the IDF path; otherwise `InvalidParameter`; unreadable or malformed: `InvalidWeatherFile`; either gives no text), validates once, writes the document, saves it with `IdfFile` when `IdfFileRequest.Write` is set, and returns `IdfConversion` (text or `null` when blocked, provenance, whether the file was written, all diagnostics). |
| `IdfWeather` | `FromBytes(fileName, bytes)`: the weather file's header (`EpwHeader`), its file name, and the SHA-256 of its bytes (64 lower-case hexadecimal digits), so that the IDF records the file it was written for (GLOBAL.md scientific rule 2). |
| `IdfFile` | `Save(path, text, overwrite)`: UTF-8 without a byte-order mark, only to an absolute path in an existing folder (the folder is not created), never over an existing file unless `overwrite`. |
| `EpwHeader` | `Parse(text)`: the header of an EnergyPlus weather file (D-130), read from text so that tests need no file: the `LOCATION` line (`EpwLocation`: city, state or province, country, source, WMO number, latitude, longitude, time zone, elevation), the `GROUND TEMPERATURES` line (`EpwGroundTemperatures`: each depth and its twelve monthly values), and a check of the `DATA PERIODS` line that the data are hourly. Only the first eight lines are read. A missing or short line, a field that is not a number, a location outside the limits of `Site:Location` in the 26.2 IDD (latitude ±90°, longitude ±180°, time zone −12 to +14 h, elevation −300 m to below 8900 m), or data that are not hourly is the error `InvalidWeatherFile`, naming the line and the field. |

Fifteen digits are formatted identically by .NET Framework 4.8 and .NET 8 (the round-trip format `R` is not), and the rounding, at most 5e-15 relative, is far below every tolerance of `ToleranceSettings`. |

## Component

*Convert2IDF* (2IDF) in panel *5 Convert* is a thin adaptor over `Convert2Idf` (GLOBAL.md architecture rule 3): it reads its inputs, runs the service, shows every diagnostic as a runtime message (errors, warnings, info as remarks), and sets its outputs. The component does not run EnergyPlus.

| 0 | Building | Bldg | item | An `IGeneratedBuilding` from a floor aggregator. |
| 1 | Envelope | Env | item, optional | An envelope preset, for example from *Envelope Preset*; the illustrative `ExampleEnvelopePresets.Example` when neither it nor *Construction* is connected; connecting both is an error. A connected input that yields no envelope preset (for example from an *Envelope Preset* with an error) also falls back to the example, with the warning `Envelope is connected but yields no envelope preset; the Example Envelope is used instead.` |
| 2 | EnableInternalWallHeatTransfer | IWHT | item | Boolean, default `false` (D-069): walls between zones paired, else adiabatic. |

Drive-relative (`C:model.idf`) and root-relative (`\model.idf`) paths are rejected (`InvalidParameter`), because they depend on the process's current folder. |

A file is written only when *Write* is true, *Path* is fully qualified and its folder exists, and the file does not exist or *Overwrite* is true; otherwise the error `InvalidParameter`, `FileWriteFailed`, or `FileExists` is shown, *Written* is false, and the *IDF* text is still output. Keep *Write* false while editing a definition: every solve with *Write* and *Overwrite* true rewrites the file.

## Validation gate

`BuildingValidator` (with the writer's tolerances) runs first (GLOBAL.md scientific rule 6). A failed enforced check returns the error `ValidationFailed`, naming the failed checks, and no document. With `OverrideValidation` the file is written, the warning `ValidationOverridden` is returned, and the header records `Validation: FAILED`, every failed check (`  FAIL <check>: <detail>`), and `OVERRIDE: converted despite failed validation`.

## File layout

Every object is written at least up to its `\min-fields` in the EnergyPlus 26.2 IDD, the fields BEMGen does not set holding the IDD defaults explicitly (for `ZoneHVAC:IdealLoadsAirSystem`: no humidification, no outdoor air, no economizer, no heat recovery). Objects are written in a fixed order, each with one field per line and its field name as a comment (hourly values six to a line, a vertex's three coordinates on one line):

1. Header comments: code version (`BuildInfo.InformationalVersion`), the EnergyPlus version (26.2) and the weather file the IDF was written for, or that none was given, the weather record (`Weather: …`, D-130), the envelope preset, its infiltration (D-124; for example `Infiltration: 0.3 AirChangesPerHour (EnergyPlus AirChanges/Hour), schedule Example Always On`), the heat-transfer options, the four lines of the [site record](#site-record), the first day of the year, the calendar (D-126; `none (BEMGen presets; run period 2007, 1 January a Monday)` or, for example, `2007 (1 January a Monday), holidays 01-01, 12-25`), the ground temperatures (`Ground temperatures: …`, D-130), the validation result, the building's provenance tree, every zone with its multiplier and source zones (GLOBAL.md scientific rule 2), and the shading of unmodelled storeys (`Shading: …`, the text of the provenance line `SHADING:`).
2. `Version` (26.2), `SimulationControl` (no sizing, no HVAC sizing simulation; run on the weather-file run periods only; no design days are written), `Building`, `Timestep` (6), `RunPeriod`, `GlobalGeometryRules`, `Site:Location` when a weather file is given (see [Weather](#weather)), `Site:GroundTemperature:BuildingSurface`.
3. `ScheduleTypeLimits` (`BEMGen Fraction` 0–1, `BEMGen Temperature` unbounded, and when needed `BEMGen Activity Level`, not negative, and `BEMGen Control Type` 0–4), `Schedule:Constant` (the default activity level `BEMGen Activity Level` when a program uses it, and one control type schedule for each kind of thermostat used), then each schedule as its day, week, and year objects, in order of first use (zone by zone, loads before setpoints).
4. The opaque materials, each by its kind (`Material`, `Material:NoMass`, `Material:AirGap`), then the window's materials (`WindowMaterial:SimpleGlazingSystem`, or each `WindowMaterial:Glazing` and `WindowMaterial:Gas` once), then `Construction`: only those used, in the envelope preset's order, then the slices of the removed slabs' construction (`{name} Half`, [below](#removed-slabs-as-internal-mass)). A layer without a roughness is `MediumRough`; its absorptances are written up to the last one given, blanks before it meaning EnergyPlus's defaults, and none when none is given. A simple glazing without visible transmittance leaves the field out, so EnergyPlus calculates it. The window construction is named after the window: a simple glazing's construction has the glazing as its one layer, a layered window's lists its glass and gas layers from the outside in.
5. `Zone`, in building order.
6. `BuildingSurface:Detailed` in building surface order (the pieces of a split surface one after another), then `FenestrationSurface:Detailed`, then `InternalMass` (removed slabs, each exposed face a half slice of the slab, then a construction set's added masses), then `SurfaceProperty:IncidentSolarMultiplier` (a construction set's, one per window), then `Shading:Building:Detailed` (the shading surfaces of unmodelled storeys).
7. Loads, zone by zone in program order, each zone's `ZoneInfiltration:DesignFlowRate` from the envelope after its program loads (D-124); then, for every conditioned zone, `ZoneControl:Thermostat`, its `ThermostatSetpoint:DualSetpoint`, `ThermostatSetpoint:SingleHeating`, or `ThermostatSetpoint:SingleCooling` (D-126), `ZoneHVAC:IdealLoadsAirSystem`, `ZoneHVAC:EquipmentList`, and `ZoneHVAC:EquipmentConnections`.
8. The research outputs (`IdfOutputs.Research`, D-130; see [Outputs](#outputs)): `Output:VariableDictionary`, `Output:SQLite`, `OutputControl:Table:Style`, `Output:Table:SummaryReports`, `Output:Variable` (hourly, every zone), and `Output:Meter` (hourly, each only when the building uses it).

The same building, envelope, and options always give the same text.

### Site record

Four header lines identify the site (experiment outputs [§7](../research/experiment-outputs.md#7-site-record), D-130), so that the record travels with the file: the EnergyPlus runner reads them back by these exact prefixes (`IdfSiteRecord`). Each is one line, deterministic, and free of code versions (the code version has its own header line); no other header line starts with `Site `.

| Line | Content |
| --- | --- |
| `Site building: floors P1x1,P1x2,P1x1; P1=[…]` | What identifies the building before zoning, from its provenance: each floor entry of the building in order, as its plan's number and its count, then each distinct plan, numbered in order of first use, as its provenance tree on one line: the generator or transform with its parameters (and seed, where a generator has one), the provenance of its inputs in braces. For example `floors P1x1,P2x1,P1x1; P1=[LinearPlanGenerator CorridorWidth=2 …]; P2=[TransformPlan … {LinearPlanGenerator …}]`. Every zoning of one building has the same line. |
| `Site zoning: simplifier …; aggregator …; IWHT=… FHT=…` | The distinct simplifiers of the floors with their parameters, the floor aggregator with its parameters except `Multipliers` and `Storeys` (which follow from the floors of the building line, so every building shares the zoning line of one configuration), and the heat-transfer options as `true` or `false`. For example `simplifier PerimeterCore PerimeterDepth=4.57; aggregator SingleZonePerFloorType; IWHT=true FHT=true`. |
| `Site weather: <file name> sha256 <hex>` | The weather file and the SHA-256 of its bytes (64 lower-case hexadecimal digits), or `Site weather: none`. |
| `Site envelope: <name>` | The envelope preset's name. |

### Names

Names come from zone and surface IDs (`L0/US1`, `L0/US1/W1`); a split surface's pieces are `<id>#1`, `<id>#2`, … (a floor or ceiling split for its holes and then into convex pieces is numbered on across both splits); shading surfaces `S<k>/<wall ID>`, with `k` the storey's index in the assembled stack; windows `<wall>/Win<k>`; loads `<zone> <LoadType> <LoadBasis>`, or `<zone> <LoadType> <end use> <LoadBasis>` when the zone holds more than one end use of that type (D-126); infiltration `<zone> Infiltration <InfiltrationBasis>`; internal masses `<zone> Internal Mass <k>`; HVAC objects and nodes `<zone> Thermostat`, `<zone> Ideal Loads`, `<zone> Supply Inlet`, …; schedules keep their names, with `Day <k>` and `Week <k>` for their parts. Names are unique within each group in which EnergyPlus compares them, ignoring case (zones; surfaces, windows, internal masses, and shading surfaces together, EnergyPlus's `AllShadingAndHTSurfNames`; schedules; …): IDF's reserved characters (`,` `;` `!`) become `_`, a name longer than 100 characters keeps its start and ends with `~` and an FNV-1a hash of the whole name, and a name already taken gets `~2`, `~3`, ….

## Weather

A weather file (EPW) is given to `Convert2Idf.Run` as a path, or to the writer as `IdfOptions.Weather` (D-130). The writer reads only its header (`EpwHeader`) and passes nothing else on: the file itself is given to EnergyPlus when it runs.

- **With a weather file**, the IDF holds `Site:Location` from the `LOCATION` line, named `<city> <state or province> <country>` (the empty parts left out, under the [name rules](#names)), with its latitude, longitude, time zone, and elevation (the five fields of the IDD minimum). The header says `EnergyPlus 26.2 input file, written for the weather file <file name>.` and records `Weather: <file name>, SHA-256 <hex>; <city>, <state>, <country> (<source>, WMO <number>), latitude …, longitude …, time zone …, elevation … m`. Provenance gains `WEATHER: <file name> sha256 <hex>; <the same location>`.
- **Without one**, there is no `Site:Location`, EnergyPlus takes the location from the weather file it runs with, the header says so and records `Weather: none`, provenance records `WEATHER: none given (EnergyPlus takes the location from the weather file it runs with)`, and the info `NoWeatherFile` is returned.
- **The run period stays the building's calendar** ([Schedules](#schedules)): EnergyPlus reads the weather file's hours in order whatever years it records. No sizing: `SimulationControl` keeps sizing off and no design days are written, because the ideal loads have no capacity limit (D-112).

## Outputs

The outputs follow [Experiment outputs](../research/experiment-outputs.md), which fixes what each site must yield and from which EnergyPlus output each quantity comes. They are one named set, `IdfOutputs.Research` (`IdfOutputSet`: its keys, frequency, variables, and meters with the source each needs), so that a later selectable set needs no new mechanism; the set is not a component input. They are written after the HVAC objects, in this order:

1. `Output:VariableDictionary` `IDF`, so that a reader can see what is available, and `Output:SQLite` `SimpleAndTabular`.
2. `OutputControl:Table:Style` `CommaAndHTML` and `Output:Table:SummaryReports` `AllSummary` (the *Building Area* table with the total and net conditioned area, the zone summary, and the hours a setpoint is not met).
3. `Output:Variable` with key `*` at `Hourly`: `Zone Mean Air Temperature`, always; and, as diagnostics when some zone is conditioned, `Zone Ideal Loads Zone Sensible Heating Energy`, `Zone Ideal Loads Zone Sensible Cooling Energy`, `Zone Ideal Loads Zone Total Heating Energy`, and `Zone Ideal Loads Zone Total Cooling Energy`.
4. `Output:Meter` at `Hourly`, only for what the building uses, because EnergyPlus warns about a meter with nothing on it:

   | Meters | Written when |
   | --- | --- |
   | `Heating:DistrictHeatingWater`, `Cooling:DistrictCooling`, `Heating:EnergyTransfer`, `Cooling:EnergyTransfer`, `DistrictHeatingWater:Facility`, `DistrictCooling:Facility` | some zone is conditioned |
   | `Electricity:Facility` | some zone has lights or electric equipment |
   | `InteriorLights:Electricity` | some zone has lights |
   | `InteriorEquipment:Electricity` | some zone has electric equipment |
   | `NaturalGas:Facility`, `InteriorEquipment:NaturalGas` | some zone has gas equipment |
   | `WaterSystems:DistrictHeatingWater`, `DistrictHeatingWater:Facility` | some zone uses hot water |

   A meter listed twice (`DistrictHeatingWater:Facility`) is written once, where it first applies. Whether a building uses a source is read from the objects written: an ideal-loads system, `Lights`, `ElectricEquipment`, `GasEquipment`, `WaterUse:Equipment`.

## Ground temperatures

`Site:GroundTemperature:BuildingSurface` holds the rule "indoor minus 2 °C" (D-130; the owner's decision of 2026-10-11, the EnergyPlus documentation's rule of thumb for large slabs), computed by `GroundTemperatureRule`:

- T_g,m = T_in,m − 2 °C for each month m.
- T_in,m is the mean over the hours of month m, on the run calendar (hour 0 is 1 January of the non-leap run year), of the building's hourly setpoint: the mean over the conditioned zones weighted by floor area × multiplier. A zone's hourly setpoint is the midpoint of its heating and cooling setpoints where it has both, and the one it has otherwise.
- A building without a conditioned zone, or whose conditioned zones have no floor area (the zero-denominator guard), uses T_in = 20 °C, and so 18 °C, the value used before, with the info `GroundTemperatureDefault`.
- The envelope's ground-floor construction is kept, so both converters describe the ground floor alike. The weather file's own ground temperatures are read (`EpwHeader`) but not used: the F-factor method that would use them waits for a sourced F-factor (D-023, the stage note's Part B.4).
- The header records the rule and the twelve values (`Ground temperatures: indoor minus 2 C, …; January to December: …`), and provenance the line `GROUND: indoor minus 2 C; <twelve values>` (or `GROUND: no conditioned zone, so 20 C indoor minus 2 C; …`).

**Across levels of detail** (the owner, 2026-10-11). The mapping from the zones' setpoints to the ground temperature is fixed, and that is all the rule promises. Its result follows each zoning's own zones and their merged setpoints, so it may differ between zonings; that difference is one of the effects the study characterises, not a defect. Merges weight setpoints by floor area over the conditioned sources (ADR-005, ADR-018), and a merge that conditions an unconditioned zone gives it the merged setpoint. The tests check that the canonical linear plan (every conditioned program at 21 and 24 °C) gives the same twelve values under every simplifier and aggregator, within the central schedule tolerance, and so does the same plan with the dwellings at 20/26 °C and the corridor at 16/28 °C under every simplifier but *Perimeter Core*. Two cases differ, both found in the build and kept as characterisations:

- ***Perimeter Core* with programs of different setpoints.** It splits the unconditioned stair among perimeter zones, each of which takes the setpoint of its own conditioned sources over its whole floor area, so the stair's area is weighted with local setpoints instead of the building's mean. With the 20/26 and 16/28 °C presets, January's ground temperature is 20.880 °C under *Perimeter Core* against 20.889 °C in the reference (`IdfGroundTemperatureTests` keeps this as a characterisation).
- **A merge of zones with different sides**, as the stage note foresaw: with the extended programs of `IdfExtendedProgramMatrixTests` (a heating-only corridor), every merge that joins it with the dual-setpoint dwellings gives a January ground temperature of 20.889 °C against 20.444 °C in the reference, because the merged zone's heating setpoint averages over both programs and its cooling setpoint over the dwellings only.


## Geometry

- **Coordinates.** Vertices are the building's own coordinates in metres, the same as the pipeline's and *Convert2BEM*'s plan frame. `GlobalGeometryRules` uses relative coordinates with every zone origin at 0 and no zone rotation, so the coordinates are used as they are, and `Building` *North Axis* is the building's orientation (`IGeneratedBuilding.OrientationDegrees`, the clockwise rotation of plan north from true north). EnergyPlus therefore sees the same true azimuths as validation does.
- **Vertex order.** Counter-clockwise seen from outside the zone, starting at the upper-left corner (D-091): a wall from its top start corner (the wall runs with its zone on the left, so its outside faces right); a ceiling or roof seen from above from its northernmost, then westernmost vertex; a floor seen from below from its northernmost, then easternmost vertex. Floors face down, ceilings and roofs up, walls and windows out of their zone.
- **Surface types.** Walls are `Wall`; floors `Floor`; ceilings `Roof` when they face outdoors (roofs and terraces, ADR-015), otherwise `Ceiling`.
- **Zones.** Every zone states its multiplier, volume, and floor area (one instance) instead of letting EnergyPlus compute them; a zone spanning storeys (*Single Zone per Floor Type*, *Single Zone Building*) has no surface for the slabs inside it. A zone of several pieces on one storey (*Semantic Merge* or *Conditioned Merge* with *Join Pieces* true, D-123) is one `Zone` as well: its floor area and volume are the sums over its pieces, and it holds the surfaces of every piece, the walls numbered on across the pieces and one floor and one ceiling per piece (`<zone>/F1`, `<zone>/F2`, …). EnergyPlus takes a zone as a set of surfaces and as one air volume, so the air of the pieces is one volume there. The writer needed no change for this.
- **Collinear vertices**, which the pipeline keeps where another zone's vertex meets an edge (ADR-002), are removed: a vertex within the distance tolerance of the segment joining its neighbours is dropped, from the start of the ring, until none is left.
- **Zero-width parts.** The pipeline no longer produces them on generated plans (floors and ceilings are clipped from conformed footprints, ADR-002, and `IdfTypologyTests` asserts that no rotated conversion warns), so this handling and the next are a guard for buildings from elsewhere. Clipping on the grid can leave a floor or ceiling with a part of no width (D-090): a spike, where the boundary runs out to a tip within the distance tolerance of the line through its neighbours and straight back, or an excursion out and back through a repeated vertex. A spike tip is removed with the collinear vertices; a ring still not simple (two vertices or two non-adjacent edges within the distance tolerance) is rebuilt as the union of its own region, which drops such parts, with its vertices put back on the original ones. The rebuilt rings that are not slivers must have the piece's area within the relative area tolerance plus the area of the rebuilt slivers (an excursion subtracts its thin area from the net area and the union adds it back as a sliver); otherwise the ring crosses itself or encloses area twice, is not a zero-width part, and the conversion fails with the error `DegeneratePolygon` instead of writing less area. Either repair is reported with the warning `SliverOmitted`, which names the zone, whether the surface is a floor or a ceiling, its elevation, the area of the slivers omitted, and the number of spikes and excursions removed with the area they changed; the region and its area do not change beyond the tolerance.
- **Holes.** EnergyPlus surfaces cannot have holes. A floor or ceiling with holes (courts, ring zones, ring cores) is cut by one line parallel to the y axis through the middle of each hole's x-range and clipped to the strips between the cuts; every hole is crossed by its own cut, so no piece keeps a hole. The pieces have the polygon's area (checked within the relative area tolerance); clipping rounds to the distance grid, so piece vertices are put back on the polygon's own vertices. The info `SurfaceSplit` names every split surface.
- **Convex outdoor surfaces** (design note 2026-10-11 part D.2). EnergyPlus projects every shading surface onto every receiving surface and clips the polygons, which is reliable only for convex surfaces: a non-convex casting surface is a severe error ("shadowing values may be inaccurate"), a non-convex receiving surface a warning. Every surface written `Outdoors` that is not convex (roofs and exposed floors of L, U, court, and hub footprints, and the pieces a hole split leaves; walls are rectangles) and every shading surface is therefore cut into convex pieces with the same total area (`IdfConvex`), reported with the info `SurfaceSplit`. Surfaces on the ground, adiabatic surfaces, and surfaces between zones take no part in shading and stay whole. The polygon is projected on its own plane; while a piece has a reflex vertex (one more than the distance tolerance inside the segment joining its neighbours), it is cut from that vertex along the extension of one of its two edges to the first point of the boundary met. The vertex is then no longer reflex in either piece and the point met adds none, so a polygon with r reflex vertices gives at most r + 1 pieces, and a rectilinear one gives rectangles. Of all candidate cuts the shortest is taken, ties going to the first reflex vertex in ring order and to the extension of the edge into it, so the split is deterministic and gives few pieces. Polygon vertices are kept exactly, a cut's end on an edge is interpolated on it, and collinear vertices are removed from each piece. Each piece keeps the surface's orientation and starts at its upper-left corner seen from outside (D-091). A cut that would cross a window is not taken, and each window is written in the piece that holds it (its host is that piece); when every cut crosses a window, the conversion fails with the error `WindowBlocksConvexSplit` naming the wall, and no window is moved or dropped. Walls are rectangles in every building the pipeline makes, so no wall is split and no window changes host. A convex surface is written as before. The roof and exposed-floor areas, and with them every invariant and the infiltration (whose exterior areas come from the building), do not change.
- **Slivers.** Where storeys touch along an edge, clipping on the grid can leave a piece of floor or ceiling narrower than the distance tolerance (about 1e-6 m wide and a few 1e-6 m² in area; D-090). A piece is a sliver when removing collinear vertices leaves fewer than three, or when its area is at most the distance tolerance times its perimeter (its mean width is then at most twice the tolerance; a real 1 m² surface has 4e-6 m² of this bound). It is not written, and the warning `SliverOmitted` names its surface and area; its partner omits the same piece. A floor or ceiling that is nothing but slivers is omitted before partners are matched, so it is neither paired nor reported unpaired (the two sides of such a sliver can clip to no overlap at all).
- **Short edges.** EnergyPlus merges vertices closer than about 0.01 m (`IdfDefaults.EnergyPlusVertexMergeDistance`, EnergyPlus's own distance, not a BEMGen tolerance). Every written surface and window with an edge shorter than that gets the warning `ShortEdge`; the file is still written. No conversion of the tests has one, the rotated and moved plans included.
- **Windows** are `FenestrationSurface:Detailed` rectangles in their wall at their offset and sill (D-039), with the wall's vertex order. A window in a wall that is not written `Outdoors` is the error `InteriorWindow` (no generator places one).

## Shading of unmodelled storeys

Unmodelled storeys cast shadows (design note 2026-10-11 part G). `IdfShadingSurfaces` writes the surfaces of the shared rule `UnmodelledStoreyShading.Of` (`Lod.Core.Conversion`, also used by *Convert2BEM*) as `Shading:Building:Detailed`: the outdoor walls of every storey of the assembled stack that no zone of the building covers in height, at their true elevations, windows included in the opaque surface. Under *Stacked Floor Zone Multiplier* these are the storeys its multiplied storeys stand for; *Stack*, *Single Zone per Floor Type*, and *Single Zone Building* model every storey and write none. Each is a wall's rectangle with a wall's vertex order (top of the start, bottom of the start, bottom of the end, top of the end), in building coordinates, so it rotates with the north axis as the building's surfaces do; the transmittance schedule is blank (always opaque). It goes through the convex split like an outdoor surface; a rectangle stays whole. The header line `Shading:` and the provenance line `SHADING:` record their count, storeys, and area. The shading is not part of the building: validation and every zone invariant ignore it.

## Heat transfer between zones

Each surface's boundary comes from `HeatTransferOptions.Exported` (D-069, D-077), as in *Convert2BEM*:

| Building surface | Written |
| --- | --- |
| `Outdoors`, `Ground`, `Adiabatic` | the same keyword; `Outdoors` surfaces are sun and wind exposed, the others not |
| Interzone, its option off | `Adiabatic` |
| Interzone, its option on | `Surface`, with its partner in the adjacent zone as boundary object |
| Interzone, option on, zones of different multipliers | `Adiabatic` on both sides, with the warning `InterzoneMultiplierMismatch` naming both |

Partners are found in the building: a wall in the adjacent zone running the other way between the same end points, at the same elevation and height; a floor or ceiling of the other kind in the adjacent zone at the same elevation and with the same polygon (equal area and overlap within the relative area tolerance). A surface without a partner is the error `UnpairedInterzoneSurface`. The first surface of a pair in building order defines the geometry: its partner's pieces are its pieces, each with the vertices in reverse order. A floor uses the interior floor construction and the ceiling below it the reversed one; of two walls between zones, the one whose zone ID sorts after the other zone's ID (ordinal) uses the reversed interior wall (`ConstructionRoles`, the one rule for both converters, ADR-010), so both sides of every pair list the same layers in opposite order. *Stacked Floor Zone Multiplier* buildings have no floor or ceiling between storeys to pair: those pieces are adiabatic in the building itself (D-075).

## Constructions

`ConstructionRoles.Of` (`Lod.Core.Conversion`) gives each surface its construction role from its kind and exported boundary, and the envelope preset its construction ([convert2bem.md](convert2bem.md#constructions), [envelope presets](../research/envelope-presets.md)). Internal masses use the preset's internal-mass construction, written as a slice of it ([below](#removed-slabs-as-internal-mass)). Materials are written with roughness `MediumRough` and EnergyPlus's default absorptances (thermal 0.9, solar 0.7, visible 0.7) unless a layer's finish gives them.

### Construction sets

A `ConstructionSet` (`Lod.Core.Envelope`, D-137) holds one construction or a status per role, the window, the infiltration, and optionally mass data and a window incident solar multiplier. `Lod.ConstructionJson` imports the atlas's unified construction JSON into one ([design note](../plans/2026-10-15-construction-json.md)). The writer:

1. **Resolves the set** for the roles the building's surfaces and removed slabs use (`ConstructionSet.Resolve`):
   - a role the set lacks is an error naming it (`ConstructionMissing`, D-140), unless `IdfOptions.FillFromExample` (*Fill From Example*) is on, when it takes the Example envelope's construction with a warning (`ConstructionFromExample`, D-138);
   - the ground floor is always the Example's, information (`GroundConstructionFromExample`, D-137);
   - a blocked role the building needs stops the conversion (`ConstructionBlocked`).
2. **Plans the added mass** (`ConstructionMassAccounting`, `Lod.Core.Conversion`). When wall mass is added, the building uses the interior wall role even without interior walls, so its fallback or block applies. A blocked furnishing, or a blocked floor-distributed mass where floor capacity falls short, stops the conversion (`ConstructionBlocked`).
   - Counted floor area is Σ zone floor area × multiplier.
   - Represented interior wall capacity counts each wall between zones once; represented floor capacity counts the floor sides of slabs between storeys and each removed slab once, with the internal mass role's construction. The IDF holds each removed slab's capacity once as well (D-143, [below](#removed-slabs-as-internal-mass)). The ledger reads the building's surface areas; where the writer drops a horizontal sliver or splits a surface, the IDF's areas can differ from them by that much.
   - Each family's budget is the set's capacity per counted floor area × the counted area.
   - A shortfall becomes the recipe's area per m² of floor (the interior wall's for walls, the floor-distributed mass's for floors). An overshoot of a positive budget adds nothing and is a warning (`MassOverBudget`); a zero budget, when the source has no such inventory, adds nothing and is information (`NoMassBudget`).
   - The furnishings are added at the set's rate.
   - Each zone gets one `InternalMass` per kind, `{zone} Furnishing Mass`, `{zone} Wall Transfer Mass`, and `{zone} Floor Distributed Mass`, with area rate × the zone's floor area, so the building's totals are exact.
3. **Writes one `SurfaceProperty:IncidentSolarMultiplier` per window** when the set has a multiplier. EnergyPlus 26.2 applies it with a blank schedule: a year's transmitted solar was in the ratio 0.8276, the multiplier, with and without it (D-143).
4. **Records the set in the header**: its source (document, SHA-256, context, infiltration), whether *Fill From Example* was on, each role's construction and where it comes from, the mass ledger's operands, the multiplier, and the components the building has no geometry for.

Only a set of the whole-building scope reaches the writer: *Construction JSON* refuses a single-dwelling one, and a detailed document gives `ConstructionAssignmentUnavailable` ([construction-json.md](construction-json.md#scope), D-142).

The test `IdfConstructionJsonTests` writes the packet's three building-scope unified documents (medium office, warehouse, midrise apartment) on the linear plan through every simplifier, aggregator, and heat-transfer setting, without *Fill From Example*, and checks from the IDF text that each family's represented and added capacity meets its budget, the removed slabs' internal masses as written included.

### Removed slabs as internal mass

A slab that a merge removes (D-031) keeps its heat storage and exchange area as internal mass: `Lod.Core` gives the area as the slab area and the number of exposed faces (two for a slab between two storeys merged into one zone). An EnergyPlus `InternalMass` is one-sided, with an adiabatic back, so writing the whole slab on slab area × faces would give each face the slab's full resistance and store its heat capacity twice. D-143 writes each face as a slice instead (`Construction.Sliced(faces)`):

- the object's area is the slab area × the faces, and its construction is `{name} Half` for two faces (`{name} Slice of {n}` for more), whose massive layers have `1/faces` of their thickness and whose massless layers and air gaps have `1/faces` of their resistance, each keeping its place and finish and taking the same suffix in its name;
- the IDF then holds the slab's heat capacity once, each face sees the resistance to the slab's mid-plane, and the mass ledger's count of the slab's capacity once ([ADR-021](../decisions/ADR-021-construction-sets-and-mass-ledger.md)) agrees with the file;
- this is exact for a symmetric slab and an approximation for an asymmetric one, such as the Example interior floor (gypsum board, concrete, screed), whose halves keep every layer in order;
- a slice whose massless layer would fall below EnergyPlus's minimum resistance (0.001 m²·K/W) is the error `EnvelopeValue`, naming the layer, and no document; so is a slice layer whose name (the layer's name plus the suffix) the envelope already gives to a material;
- the slices are written after the construction set's own constructions, and one-face slabs use the slab construction itself;
- *Convert2BEM*'s *Internal Mass* output is unchanged: it is the exposed area ([convert2bem.md](convert2bem.md)).

## Loads

One object per load component (type, end use, and basis, D-047, D-126), with the load's own fraction schedule:

| Load type | Object | Basis written in its own field | Other bases |
| --- | --- | --- | --- |
| Occupancy | `People` | per floor area (`People/Area`), absolute (`People`) | per dwelling unit: the number of people of the zone's dwellings, absolute (value × dwelling count, D-126) |
| Lighting | `Lights` | per floor area (`Watts/Area`), per person (`Watts/Person`), absolute (`LightingLevel`) | absolute design magnitude, W (per dwelling unit: value × the zone's dwelling count) |
| Electric equipment | `ElectricEquipment` | as lighting (`EquipmentLevel`) | absolute design magnitude, W |
| Gas equipment | `GasEquipment` | as lighting (`EquipmentLevel`) | absolute design magnitude, W |
| Ventilation | `ZoneVentilation:DesignFlowRate` | per floor area (`Flow/Area`), per person (`Flow/Person`), absolute (`Flow/Zone`), air changes (`AirChanges/Hour`) | absolute design magnitude (`Flow/Zone`) |
| Domestic hot water | `WaterUse:Equipment` | — | always the absolute peak flow of one zone instance, with the zone for its multiplier, the load's target temperature schedule and its inlet temperature schedule as the cold-water supply temperature (D-126), and no zone heat gains; written only when a preset defines it (the example presets do not; a program JSON usually does) |

Flows are converted from m³/h to m³/s. Where EnergyPlus has no field for a basis (for example lighting in air changes per hour), the writer writes the absolute design magnitude of one zone instance, value × basis quantity (ADR-007), which EnergyPlus applies identically, because every design-level method resolves to a fixed design level of the zone and the zones state their own floor area and volume. So no load is dropped and no basis is an error. Ventilation and infiltration have the coefficients 1, 0, 0, 0, so the flow is the design flow times the schedule whatever the weather; ventilation is `Balanced` with no fan (pressure rise 0, efficiency 1). Infiltration is not a program load since D-124; see the next section.

**Program fields (D-126).** The fractions and the people's properties that were fixed writer defaults in S6 are program fields now ([domain-model.md](domain-model.md#4-loads-lodcoreloads), [ADR-018](../decisions/ADR-018-program-json-and-extended-programs.md)), and their defaults are the old values, so a program that sets none is written exactly as before:

| Object | Fields written from the program |
| --- | --- |
| `Lights` | `Return Air Fraction`, `Fraction Radiant`, `Fraction Visible` from the load's heat fractions; `Fraction Replaceable` stays 1 (`IdfDefaults.LightsFractionReplaceable`, a daylighting field, not a program field) |
| `ElectricEquipment`, `GasEquipment` | `Fraction Latent`, `Fraction Radiant`, `Fraction Lost` from the load's heat fractions |
| `People` | `Fraction Radiant` and `Sensible Heat Fraction` (the number, or `autocalculate`) from the zone's people properties; `Activity Level Schedule Name` is the zone's activity schedule: the default (constant 120 W per person) as the `Schedule:Constant` `BEMGen Activity Level`, any other as a schedule under the type limits `BEMGen Activity Level` |
| `WaterUse:Equipment` | `Target Temperature Schedule Name` and `Cold Water Supply Temperature Schedule Name` from the load's water temperatures (they were blank, so EnergyPlus's defaults applied); `Hot Water Supply Temperature Schedule Name` stays blank, and the sensible and latent fraction schedules are not written, so water adds no zone heat, as the contract keeps plant and zone gains separate |

A heat fraction in a field the EnergyPlus object lacks (latent or lost on lights, visible or return air on equipment) cannot reach the writer: a program with one is rejected when it is built (`HeatFractionNotSupported`). A per-dwelling load is the absolute design level value × the zone's dwelling count, for one zone instance; EnergyPlus applies the zone multiplier.

## Infiltration

The infiltration of the envelope preset (D-124, [ADR-017](../decisions/ADR-017-program-mix-and-building-infiltration.md)) is written once per zone, after the zone's program loads, conditioned or not, unless the zone has none of the area its basis needs (below): a `ZoneInfiltration:DesignFlowRate` named `<zone> Infiltration <InfiltrationBasis>` with the envelope's fraction schedule (one schedule shared by every zone, written once under its own name), the coefficients 1, 0, 0, 0, and the rate in EnergyPlus's own method for its basis, so that EnergyPlus multiplies the rate by that zone's own quantity, per zone instance before the zone multiplier. The writer computes no flow: no zone merge aggregates infiltration, and EnergyPlus gives each zone the flow of the surfaces and volume the file states for it.

| `InfiltrationBasis` | Design Flow Rate Calculation Method | Rate written in | EnergyPlus multiplies it by |
| --- | --- | --- | --- |
| `PerExteriorSurfaceArea` | `Flow/ExteriorArea` | `Flow Rate per Exterior Surface Area`, m³/s per m² (the rate in m³/h per m² divided by 3600) | the zone's exterior surface area |
| `PerExteriorWallArea` | `Flow/ExteriorWallArea` | the same field | the zone's exterior wall area |
| `AirChangesPerHour` | `AirChanges/Hour` | `Air Changes per Hour`, 1/h | the volume the `Zone` object states |

**Zones without the area of the basis (D-130).** A zone whose basis is per exterior surface area and which has no surface written `Outdoors`, or whose basis is per exterior wall area and which has no outdoor wall, gets no `ZoneInfiltration:DesignFlowRate`: its design flow is 0 in BEMGen (`ZoneInfiltration.DesignFlow`) and in EnergyPlus alike, so nothing is lost, and EnergyPlus would warn about the object (`Exterior Surface Area = 0. 0 Infiltration will result.`, the first run's warning 4: the core zones of *Perimeter Core*). The info `InfiltrationNotWritten` names the zones. With air changes every zone has a volume and gets its object.

**The exterior area of EnergyPlus (found by running 26.2).** What EnergyPlus counts as a zone's exterior surface area was checked by running EnergyPlus 26.2, the version at hand, on converted files with a storey moved off the one below (the file targets 25.2, with its version line changed for the run; 25.2 itself has not been run, D-112). Each zone's design flow in the `.eio` was the rate times the zone's outdoor walls, roofs, and exposed floors, with windows included in the gross areas, and without its ground floor; with `Flow/ExteriorWallArea` it was the rate times its outdoor walls alone. Surfaces with the boundary `Ground` or `Adiabatic`, and surfaces between zones, are not counted. BEMGen writes every outdoor wall, roof, and exposed floor of a zone with the boundary `Outdoors` and its full area, so EnergyPlus uses the area of the zone's own surfaces facing outdoors; the slabs between storeys that *Stacked Floor Zone Multiplier* repeats are adiabatic, as in the building itself, and are not counted. The finding is recorded in the comments of `IdfLoads.Infiltration`, and `ZoneInfiltration` in `Lod.Core.Conversion` computes the same areas for *Convert2BEM*'s *Infiltration Flows* ([convert2bem.md](convert2bem.md#infiltration)).

## HVAC and thermostats

Every conditioned zone (D-038) gets `ZoneControl:Thermostat` and the setpoint object of its sides (D-126): `ThermostatSetpoint:DualSetpoint` with control type 4 when it has both a heating and a cooling setpoint schedule, `ThermostatSetpoint:SingleHeating` with control type 1 when it has heating only, `ThermostatSetpoint:SingleCooling` with control type 2 when it has cooling only, each type with its own constant control type schedule (`BEMGen Dual Setpoint Control`, `BEMGen Single Heating Control`, `BEMGen Single Cooling Control`, written when used). Every zone also gets a `ZoneHVAC:IdealLoadsAirSystem` with no heating or cooling limit, in an equipment list connected to the zone. An unconditioned zone gets neither, but keeps its loads and infiltration.

## Schedules

Every 8760-value schedule (ADR-003) is reproduced hour by hour, to fifteen significant digits, as `Schedule:Year` over `Schedule:Week:Daily` and `Schedule:Day:Hourly`: each distinct day of the schedule is one day schedule; the year is cut into seven-day blocks from 1 January, each block a week schedule giving every weekday the day schedule of its date in the block; consecutive equal blocks share one week schedule and one period. The last block, 31 December alone, takes the other weekdays from the block before it, so it merges with that block when its day agrees. A schedule from weekday and weekend profiles is thus two day schedules, one week schedule, and one period. The holiday, design-day, and custom-day types use the Sunday day schedule, and the writer defines no holiday or special day: a program's holidays (D-126) are already in its hourly values, which carry each date's own profile, so the run period applies them without a day type of their own. A program JSON's design-day profiles are not used (they are not days of the year); the design days of the weather file, when one is added, get the Sunday profile. A schedule is written once per name and values; another schedule with the same name but other values gets its own name.

The `RunPeriod` covers 1 January to 31 December of a non-leap year with the weather file's holidays and daylight saving off, so EnergyPlus applies the hourly values on the days they were made for. Since D-126 the year and the weekday come from the building's calendar (the one calendar its zones share, `ProgramChecks.Calendar`): a program JSON built on 2014 gives the year 2014 starting on a Wednesday. Without a calendar (BEMGen's own presets) the year is the one that starts on `IdfOptions.FirstDayOfYear` (Monday if unset): 2007 for Monday (it was 2018 before D-126, also a Monday), 2017 for Sunday, 2019 for Tuesday, 2014 for Wednesday, 2015 for Thursday, 2010 for Friday, and 2011 for Saturday. A weekday given in the options that contradicts the calendar is the error `CalendarMismatch`, and so are zones on different calendars, which no single run period fits (the validation override does not lift it).

## Tests

`tests/Lod.Export.Tests` checks every part on its own (text and names, schedules, geometry, loads, the writer), and whole files by reading them back with a small IDF parser (`Support/IdfParser.cs`, `Support/IdfChecks.cs`), without EnergyPlus:

- **Counts and references:** zones, ideal-loads systems, thermostats, windows, internal masses, and load objects as in the building; every surface's zone and construction, every construction's layers, every window's wall, every load's zone and schedule, every thermostat's schedules, and every year schedule's weeks and days exist; names are unique as EnergyPlus requires and at most 100 characters.
- **Partners:** every `Surface` boundary points to a surface in another zone that points back, with its vertices reversed and its construction's layers reversed; with the options on, every surface between zones of equal multipliers is paired; with both off, none is.
- **Geometry:** every surface and window is planar and simple (no hole, slit, or repeated vertex), walls are vertical, floors face down, ceilings and roofs up, and windows face as their wall does; every surface written `Outdoors` and every shading surface is convex (part D.2), and the shading surfaces are planar and simple and have the area of `UnmodelledStoreyShading.Of`'s surfaces (`ShadingArea`).
- **Invariants against the building**, counting multipliers: floor area and volume, exterior wall, ground, roof, and exposed floor area, the floor and ceiling surface area by surface type and written boundary (ground, outdoors, partner surface, adiabatic), so a missing or extra piece shows even where the zone fields agree, internal-mass area, glazing in total and per orientation (from the window normals and the north axis), and installed and hourly scheduled magnitude per program load type, from the IDF's own design levels and expanded schedules (relative load tolerance), and the infiltration (D-124): one object per zone that has the quantity of the basis and none for the others (D-130), in the method of the envelope's basis, with the envelope's rate and schedule, whose flow from the IDF's own surfaces and volumes, as EnergyPlus reads them, equals `ZoneInfiltration.DesignFlow` zone by zone, a zone without an object having a design flow of 0, and in the installed total over every zone (`IdfInfiltrationTests`, `IdfChecks`).
- **Coverage:** the canonical linear plan (multipliers 1, 2, 1) through every simplifier and aggregator with both settings; the enclosed court, the court cluster, and the office plate (multipliers 1, 3, 1) and the stepped band (its three storeys) the same way; each of these five plans also rotated by 30° and moved by (5.3, −2.1) m, and the linear plan with an orientation of 30° (north axis and glazing per orientation end to end); on the rotated plans only zero-width parts may be omitted, and what is written of each such surface keeps its area. A plan with every load kind and basis (hot water, gas, ventilation; per person, absolute) is converted too, and the canonical linear plan through every combination with each infiltration basis. No conversion has a short edge. Negative tests break one thing in a correct file and expect the checks to name it.
- **Snapshots** (`tests/Lod.Export.Tests/Snapshots/idf-*.txt`): the minimal linear plan in full, and four combinations of the canonical plan that cover each simplifier, each aggregator, and both settings once (one file per combination of the sixteen would be tens of thousands of lines; every combination is read back instead). Numbers are compared to the building within the tolerances of `ToleranceSettings`, because they are written with fifteen significant digits. Since D-124 every snapshot has the header line `Infiltration:`, and in five of them (four of the canonical plan and the stair-bay bar's of D-123) the infiltration of every zone uses the one envelope schedule, written once, where each zone had its own aggregated schedule.
- **Convex split and shading (design note 2026-10-11, parts D.2 and G)** (`IdfConvexTests`, `IdfGeometryTests`, `IdfShadingTests`): L and U roofs and exposed floors, rotated or not, and a ring roof split for its hole and then into convex pieces give convex pieces of the same area, facing as the surface does, each from its upper-left corner, named `<id>#k`; ground, adiabatic, and interzone surfaces stay whole; a vertical L keeps a window whole by taking the cut that avoids it, and one whose every cut crosses a window is the error `WindowBlocksConvexSplit`.
