# ADR-036: Atlas program maps on the DOE program map presets, and Generator JSON from the atlas site

- **Status:** Accepted
- **Date:** 2026-10-30
- **Decision log:** [D-209](decision-log.md#d-209--atlas-program-maps-on-the-doe-programs-components-and-generator-json-from-the-atlas-site-adr-036)
- **Design note:** [atlas program picker](../plans/2026-10-30-atlas-program-picker.md), §3, §4.3, and §6 (every recommendation accepted by the owner on 2026-10-30)
- **Amends:** [ADR-018](ADR-018-program-json-and-extended-programs.md#the-atlas-window-d-208) (the atlas window, D-208) and [ADR-035](ADR-035-schedule-draw-generator-4-0-0.md) (where *Generator JSON* may come from)
- **Atlas side:** the atlas's ADR 0052, live since 2026-10-30: the site's index gives each program its `folder`, `mode`, `space_type`, and `building_type`, and a top-level `folders` with each folder's programs and, where the release has one, its `generation.json` in the store

## Context

The fifteen DOE *Programs* components give each DOE generator a map of illustrative presets (D-023, stage P7). The atlas publishes every DOE prototype's programs in five commercial families, and since its ADR 0052 the site's index says which folder, mode, and space type each program has. *Program JSON* already takes one program from the site (D-208). The owner asked that the DOE components take a whole map that way, and that *Schedule Draw*'s *Generator JSON* come from the site too.

## Decision

1. **One fixed folder per prototype.** `DoeAtlasFolders` (`Lod.Generators`) gives each DOE prototype its folder name: the nine whose prototype name is the folder's, the three detailed offices (`small-office-detailed`, `medium-office-detailed`, `large-office-detailed`), and `retail-standalone`, `retail-stripmall`, `super-market`. The folder of a family is `commercial/<template>/<folder>/`. Folders are never searched: space types repeat across folders.
2. **The index's folders are read apart from its programs.** A fault in the atlas ADR 0052 fields (a folder that is not its family, template, and building type, a folder and a program that do not list each other, a malformed `generation`, a program field that is not a text) drops all of them (`AtlasSiteIndex.FoldersFault`) but not the programs, so *Program JSON*'s window (D-208) keeps working; the DOE windows and *Schedule Draw*'s refuse with the fault.
3. **A key matches by space type, among source programs only.** `AtlasSiteIndex.MatchKeys` matches a key to the one program of the folder whose `mode` is `source` and whose `space_type` is the key, compared exactly. Programs of mode `department` and `general` are not candidates: the atlas derives them by merging source programs (their space types are `*_Mixed`, such as `Sales_Mixed` and `General_Mixed`), so they are not a standards space type of the prototype. A key with no such program is a gap; a key with more than one is ambiguous and unmatched too. A test pins, against a recorded index of the 75 folders, every family's resolved keys and gaps, that no key is ambiguous, and that no department or general program has a key's space type, so a change on the atlas side fails it.
4. **Five families.** The window offers DOE Ref pre-1980, DOE Ref 1980–2004, 90.1-2007, 90.1-2013, and 90.1-2019, the families the note reconciled, each with its coverage. The IECC templates, which hold most of the prototypes' folders too (none of the offices' or the supermarket's), are not offered: their programs were not reconciled with the DOE layouts' keys and are source only. Offering them is a separate decision.
5. **Keys without a program are refused** (the note's question 5, answer a). OK in the window stores a family with gaps, the keys left empty in the map; the solve then outputs no *Program Map*, an error that names the keys, the family, and the folder, and *Presets* and *JSON* with those positions empty, so *DOE Program Map* can complete the map by hand. Neither the illustrative preset (b) nor a crosswalk (c) fills them.
6. **One stored text.** OK downloads every matched key's program in parallel, each checked as *Program JSON*'s download is (the SHA-256 of the gzip bytes against the store path, `id`, `version`, `source.release`) and then given the program check on the component's calendar, climate zone, and context; one failure stores nothing. The map is stored as one text (`bemgen-atlas-program-map` 1.0.0: the prototype, the site, its release and manifest checksum, the family, the folder, the version, and per key the program, its store path, and its text) in the component, written by `Write` and read by `Read`, with one undo event. *Clear* in the window removes it. The solve reads no file or network.
7. **The solve shares *Program JSON*'s import.** Each key's text is imported by `ProgramJsonImporter` with the key's name, its space type (`DoeSpaceTypes.Of`), the component's *Climate Zone*, *Year*, *Holidays*, and *Context* (optional inputs appended after none, unset as on *Program JSON*), and the DOE reference building's window-to-wall ratio per orientation and skylight ratio of the key (`DoeProgramPresets.KeyRatios`), so the presets fit the generator's geometry and their window area is the illustrative map's. The new output *JSON*, after the existing three, gives each key's text in the order of *Keys*.
8. **Old definitions reopen unchanged.** No GUID changes. A definition saved before (no inputs, three outputs, no stored map) reads without the IO dialog and solves with the illustrative presets as before; the smoke check reopens one saved by the 1.7.0 plugin.
9. ***Generator JSON* from the site.** The same strip on *Schedule Draw* finds the folder of the program in its *Program JSON* by the program's `id` in the index, downloads that folder's `generation.json` from the store, checks it (the SHA-256 of its gzip bytes against its path, the decoded size the index gives, a JSON object whose `programs` names every program of the folder), and stores it as the *Generator JSON* input's value with one undo event. Where the release has no generation file for the folder it is refused with a message saying so (`AtlasSiteGenerationNotPublished`). In release 2.2.0 only 90 of the 255 folders have one, and none of the `*-detailed` office folders, so the DOE small, medium, and large office cannot take *Generator JSON* from the site: an atlas limitation, not worked around (the release's own non-detailed office folders hold programs of other IDs, which the draw would not find).

## Alternatives

- **Match across folders by name**: refused; `Retail` and several restaurant keys are names of other prototypes' programs too.
- **Match department or general programs where no source program matches**: refused; they merge source programs, which would mix programs in one key silently.
- **Fill gaps with the illustrative preset (b)** or **an owner-approved crosswalk (c)**: (b) mixes sourced and illustrative values in one map; (c) is a source decision that needs its own evidence.
- **A hidden input holding the map's text**: refused; a visible text input would invite wiring and editing a 1 MB document by hand. The text is the component's own state, like a value list's.
- **One program per key downloaded in the solve**: refused, as in D-126 and D-208; the network is used only after a click.

## Consequences

- A DOE map can now be sourced from the atlas for 153 of 153 keys (DOE Ref families), 151 (90.1-2007), or 149 (90.1-2013 and 2019); the others need a preset by hand.
- A stored map is about the size of its programs' texts, some 30 kB per key (about 1 MB for the outpatient's 32 keys), in the definition.
- The programs of the DOE offices' keys cannot be drawn until the atlas publishes a `generation.json` for the detailed folders.
- A draw's `recipe_sha256` is that of the bytes given (ADR-033 decision 10 as amended by D-207), so a `generation.json` taken from the site, compact JSON, records another checksum than the release zip's pretty-printed file of the same content; the drawn schedules are the same.
- The recorded site `tests/Lod.ProgramJson.Tests/Fixtures/site-doe/` (the 75 folders whole, and the store files of three maps and one generation file) is recorded again by `scripts/atlas-fixtures/record_site_fixtures.py` when the atlas changes them.
