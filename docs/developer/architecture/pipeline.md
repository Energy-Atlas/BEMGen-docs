# BEMGen pipeline

At Checkpoint 1 (stages S0–S4, D-030) the pipeline is complete for the linear plan; the revision stage S4.1 (D-061 to D-064) gave the plan generator one preset input per space type and added default preset components, a *Preview Location* input, and component icons; the revision stage S4.2 (D-068 to D-075, [ADR-013](../decisions/ADR-013-vertical-aggregation-methods.md)) added *Transform Plan*, made the floor aggregators designate floors and ceilings on the assembled stack, turned them into four methods, and made heat transfer between zones a conversion option; stage S5 (D-079, [ADR-012](../decisions/ADR-012-centred-windows.md)) gives every rebuilt outdoor wall one centred window with the glazed area it covers; stage S8.1 (D-082 to D-084, [ADR-006](../decisions/ADR-006-plan-generation-mechanism.md), [ADR-011](../decisions/ADR-011-minimum-wall-and-window-geometry.md)) adds a plan generator for each bar family of the *High-Density Housing* precedent study and the minimum wall and window geometry of every generator; stage S8.2 (D-084) adds the non-rectangular families without holes, the point plate, the winged band, and the open court, and makes the united zones and the edge tests of the surface builder exact on rotated plans; stage S8.3 (D-084) adds the enclosed court, the first footprint with a hole, which every simplifier and aggregator supports; stage S8.4 (D-093 to D-098, [ADR-014](../decisions/ADR-014-program-types-and-department-zoning.md)) adds the non-residential space types with their presets and default preset components, and the office plate and the cafeteria of the four-source precedent set; stage S8.5 (D-098, D-100) adds the four families that branch from a hub on the shared hub-and-arms layout, the radial lobes, the branching mall, the care hub, and the foyer with halls, and makes the perimeter zones of *Perimeter Core* keep the footprint's own vertices; stage S8.6 (D-098) adds the operating suite with separated clean and dirty routes and the court cluster, the first footprint with several holes; stage S8.7 (D-095, D-098, [ADR-015](../decisions/ADR-015-plans-per-storey.md)) adds generators that return one plan per storey and the stepped band, whose lower roofs become terraces; the revision stage S8.8 (D-108) previews a storey's floors at the storey's height, as its plan, adds the *Any Program Preset* parameter, which casts any preset to one without a space type that every preset input takes, and moves the built-in preset components to a panel of their own; stage S6 (D-112, D-113, [ADR-010](../decisions/ADR-010-convert2idf.md)) adds the envelope preset shared by both converters and *Convert2IDF*, which writes an EnergyPlus 25.2 input file. This document describes each step, the rules it applies, where results are validated, and the Grasshopper components that expose it. The domain types are described in [domain-model.md](domain-model.md), the validation checks in [validation.md](validation.md), and the `Convert2BEM` output layout in [convert2bem.md](convert2bem.md).

## Overview

```text
program presets          ProgramPreset, PresetValues                        one preset per space type, conditioned or not
  → plan generator       PlanGenerator<P, Presets>: LinearPlanGenerator |   → IGeneratedPlan        one preset input per space type; Z0: one zone per dwelling unit or department, explicit windows (ADR-011 limits)
                         StairBayBar | StairPair | GalleryBar | TerraceRow |
                         PointPlate | WingedBand | OpenCourt |
                         EnclosedCourt | OfficePlate | Cafeteria |
                         RadialLobes | BranchingMall | CareHub |
                         FoyerHalls | OperatingSuite | CourtCluster
                         MultiStoreyPlanGenerator<P, Presets>:              → IGeneratedPlan per storey, bottom-up (ADR-015)
                         SteppedBand
  (→ PlanTransform       optional: rotation about z, x-y translation        → IGeneratedPlan        D-070)
  → IPlanSimplifier      NoSimplification | SemanticMerge |                 → IFloor                Z0 | Z1 | Z2 | Z3, one centred window per rebuilt wall (D-079)
                         PerimeterCore | SingleZonePerFloor
  → IFloorAggregator     Stack | StackedFloorZoneMultiplier |               → IGeneratedBuilding    floors bottom to top as FloorEntry(IFloor, Multiplier)
                         SingleZonePerFloorType | SingleZoneBuilding
  → validation           FloorValidator, BuildingValidator                  → ValidationReport
  → Convert2BEM          Grasshopper component, HeatTransferOptions         → data trees for a ClimateStudio definition (provisional, D-023)
  → Convert2IDF          Grasshopper component over Convert2Idf (Lod.Export) → EnergyPlus 25.2 IDF text and file, not run (ADR-010, D-112)
```

- All logic lives in `Lod.Core` and `Lod.Generators`, which reference neither Rhino nor Grasshopper; their tests run with `dotnet test`. `Lod.Grasshopper` wraps each pipeline type in a Goo with a viewport preview and exposes one component per step (D-017, D-018). Every component that previews a plan, floor, or building has a last input *Preview Location* that moves only its preview (D-062, [below](#grasshopper-components-through-s88)).
- Every step returns `Result<T>`: a value or errors, plus warnings and info diagnostics with stable codes (`DiagnosticCodes`). Components show diagnostics as runtime messages (error, warning, remark); after an error there is no output.
- Pipeline objects are immutable. Every plan, floor, and building carries a `Provenance` record (operation, parameters, inputs, code version), which the *Inspect* component prints.
- Numerical tolerances come only from `ToleranceSettings` (ADR-004), the minimum wall and window geometry of the generators only from `GeometryLimits` (ADR-011). The same inputs always give the same output.
- Windows are not a separate axis (D-079, [ADR-012](../decisions/ADR-012-centred-windows.md)). Wherever zones are merged and walls are rebuilt (*Semantic Merge*, *Perimeter Core*, *Single Zone per Floor*, *Single Zone per Floor Type*, *Single Zone Building*), every outdoor wall carries exactly one window, centred on it by the generator's rule (D-026), whose area is the glazed area of the source windows it covers; a wall without glazing has none. Glazed area is conserved per wall, and so per façade, orientation, and building; window positions are not. *No Simplification*, *Stack Floors*, and *Stacked Floor Zone Multiplier* keep their input's windows. The window levels W1–W5 of the earlier research brief are dropped.

## Steps

### 1. Program presets

| | |
| --- | --- |
| Types | `Schedule`, `LoadDefinition`, `Thermostat`, `ZoneProgram`, `ProgramPreset`, `PresetValues`, `PresetLoadValue`, `ExampleResidentialPresets`, `ExampleNonResidentialPresets`; envelope (S6): `EnvelopePreset`, `EnvelopeValues`, `Construction`, `Layer`, `GlazingSpec`, `ExampleEnvelopePresets` |
| Components | Panel *1 Program*: *Schedule*, *Load*, *Program Preset* (input *Conditioned*), and the parameter *Any Program Preset* (S8.8); panel *1 Program Presets* (S8.8): *Dwelling Unit Preset*, *Corridor Preset*, *Stair Preset*, the fifteen non-residential default preset components (*Office Preset* … *Service Preset*, S8.4), and *Envelope Preset* (S6) |
| Decisions | D-024, D-026, D-038, D-047, D-061, D-094, D-097, D-108; ADR-003, ADR-005, ADR-007, [ADR-014](../decisions/ADR-014-program-types-and-department-zoning.md) |

- A program preset holds the zone program of one space type and the window-to-wall ratio in [0, 1) that the plan generator uses (D-024, D-026). Its name is descriptive only: it appears in reports, provenance, and messages and is never used for matching (D-061).
- An any-program preset (S8.8, D-108, [ADR-014](../decisions/ADR-014-program-types-and-department-zoning.md)) has no space type: `ProgramPreset.SpaceType` is `null` and `IsAnyProgram` is `true`. Every preset is created with a space type; `AsAnyProgram()` returns it without one and keeps its name, program (loads, schedules, conditioning, setpoints), and WWR.
- `PresetValues` holds the plain values a preset is built from: name, space type, WWR, *Conditioned*, constant heating and cooling setpoints in °C, and the loads (`PresetLoadValue`: type, basis, value, fraction schedule). `ToPreset()` builds the preset and reports every invalid value at once; a conditioned preset gets constant setpoint schedules named `"{Name} Heating Setpoint"` and `"{Name} Cooling Setpoint"`, and an unconditioned one ignores the setpoints.
- Conditioning comes from the preset (D-038): a conditioned program has a thermostat (heating and cooling setpoint schedules); an unconditioned program has no setpoints.
- Schedules have 8760 hourly values, either fractions or temperatures (ADR-003).
- Load types: Occupancy, Lighting, ElectricEquipment, GasEquipment, DomesticHotWater, Ventilation, Infiltration. Each load has one basis: PerFloorArea, PerPerson, Absolute, PerExteriorWallArea, or AirChangesPerHour (ADR-007). A program holds at most one load per type and basis, so a load type may have components in several bases, which add up; a zone's design occupants are the sum of its occupancy components (D-047). Magnitudes are people, W, or m³/h.
- `ExampleResidentialPresets` hold illustrative round numbers for development and tests, not DOE prototype values: dwelling unit and corridor conditioned, stair unconditioned. Each is available as values (`DwellingUnitValues`, `CorridorValues`, `StairValues`) and as the preset built from them (`DwellingUnit`, `Corridor`, `Stair`). The default preset components *Dwelling Unit Preset*, *Corridor Preset*, and *Stair Preset* take these values as their input defaults, so each works with nothing connected, and each shows the remark "Illustrative values; not sourced from DOE prototypes or standards."
- An envelope preset (S6, [ADR-010](../decisions/ADR-010-convert2idf.md)) is not part of a program preset: it holds one layered construction per envelope role and the window's simple glazing, is the same at every level of detail, and is given to the converters (*Convert2BEM*, *Convert2IDF*). `ExampleEnvelopePresets.Example` holds illustrative values, not taken from any standard ([envelope presets](../research/envelope-presets.md)).
- `ExampleNonResidentialPresets` (S8.4, ADR-014) hold illustrative presets, all conditioned, for the space types of the non-residential departments (D-097): `Office`, `Core`, `Retail`, `Mall`, `Kitchen`, `Dining`, `OperatingTheatre`, `CleanCorridor`, `DirtyCorridor`, `ClinicalSupport`, `CareBedroom`, `CareCommunal`, `Lobby`, `ActivityHall`, and `Service`; the kitchen has gas equipment and, like the operating theatre, ventilation in air changes per hour; the retail schedules have their own Saturday and Sunday profiles. One default preset component per type, *Office Preset* to *Service Preset*, takes these values as input defaults with the same remark. Values and schedules: [program presets](../research/program-presets.md) §2.2.

### 2. Plan generation

| | |
| --- | --- |
| Types | `PlanGenerator<TParameters, TPresets>` → `IGeneratedPlan`: `LinearPlanGenerator`, `StairBayBarGenerator`, `StairPairGenerator`, `GalleryBarGenerator`, `TerraceRowGenerator`, `PointPlateGenerator`, `WingedBandGenerator`, `OpenCourtGenerator`, `EnclosedCourtGenerator`, `OfficePlateGenerator`, `CafeteriaGenerator`, `RadialLobesGenerator`, `BranchingMallGenerator`, `CareHubGenerator`, `FoyerHallsGenerator`, `OperatingSuiteGenerator`, `CourtClusterGenerator`, each with its `<Family>Parameters` and `<Family>Presets`; `MultiStoreyPlanGenerator<TParameters, TPresets>` → `IReadOnlyList<IGeneratedPlan>`, one plan per storey bottom-up (ADR-015): `SteppedBandGenerator` with `SteppedBandParameters` and `SteppedBandPresets`; `GeometryLimits`; `PlanTransform.Apply(IGeneratedPlan, rotationDegrees, translationX, translationY)` → `IGeneratedPlan` |
| Components | *Linear Plan Generator*, *Stair Bay Bar*, *Stair Pair*, *Gallery Bar*, *Terrace Row*, *Point Plate*, *Winged Band*, *Open Court*, *Enclosed Court*, *Office Plate*, *Cafeteria*, *Radial Lobes*, *Branching Mall*, *Care Hub*, *Foyer Halls*, *Operating Suite*, *Court Cluster*, *Stepped Band*, *Transform Plan* |
| Decisions | D-009, D-015, D-026, D-039, D-061, D-070, D-082, D-083, D-084, D-093, D-094, D-095, D-097, D-098, D-100; ADR-002, [ADR-006](../decisions/ADR-006-plan-generation-mechanism.md), [ADR-011](../decisions/ADR-011-minimum-wall-and-window-geometry.md), [ADR-013](../decisions/ADR-013-vertical-aggregation-methods.md), [ADR-015](../decisions/ADR-015-plans-per-storey.md) |

- Presets (D-061): a generator takes a typed preset record with one preset per space type it places, a `PlanPresets` whose `Slots` list its inputs as `PresetSlot(Input, SpaceType, Preset)`. For the linear block this is `LinearPlanPresets(DwellingUnit, Corridor, Stair)`. Before the layout is built every slot is checked: a preset of another space type is the error `PresetSpaceTypeMismatch` (one per wrong slot, naming the input, both space types, and the preset), a missing preset the error `MissingPreset`. Each zone gets the preset of the slot of its space type; provenance records `Presets=DwellingUnit:<name>;Corridor:<name>;Stair:<name>` in slot order, with each slot's space type. An any-program preset (S8.8, D-108) is accepted on every slot: the zones keep the space type of the layout and take the preset's program and WWR, and the plan records `AnyProgramPreset.<Input>=<name>` for each such slot (for example `AnyProgramPreset.Corridor=Example Office`), so the change of program is never silent (GLOBAL.md scientific rule 3). A plan of typed presets records no such parameter and is unchanged.

- Mechanism (ADR-006): one generator per typology family of the precedent study ([four-source families](../research/precedents/syn-typologies.md), D-093; the nine *High-Density Housing* families are carried as `SYN-TYP-001`–`009`, [hdhm-typologies.md](../research/precedents/hdhm-typologies.md), D-082, D-083), each a `PlanGenerator` subclass in `Lod.Generators/<Family>/` whose layout returns the footprint and the zones as polygons; the base checks the presets, builds the surfaces, places the windows, and records provenance. Layouts are axis-aligned in the plan frame (origin at the south-west corner, the bar along plan east); *Orientation* turns plan north and *Transform Plan* moves the result. Parameter records of S8 have a static `Default` with the ADR-006 defaults, which the components use as their input defaults. A parameter that would remove one of the family's essential relationships (a count below the family minimum) or a length that is not positive is the error `InvalidParameter`. Lengths are metres.
- Linear block (`HDHM-TYP-009`, double-sided internal corridor bar): a full-depth stair at the west end (`ST`), a double-loaded corridor (`CO`), and one row of equal dwelling units on each side (`US1…`, `UN1…`); one zone per dwelling unit (D-009). Checked against the family's rules in S8.1 and unchanged.
- Stair bay bar (`HDHM-TYP-001`): `BayCount` (≥ 2, default 3) stair bays of dwelling | stair | dwelling through the full depth (`UnitWidth` 7 m, `StairWidth` 3 m, `Depth` 12 m): stairs `ST1…STn`, then dwellings `U1…U2n`, west to east; each stair adjoins the two dwellings of its bay; no corridor.
- Stair pair (`HDHM-TYP-008`): one stair bay as its own building, with the same layout code (`StairBayLayout`): `ST1`, `U1`, `U2`; defaults as the stair bay bar.
- Gallery bar (`HDHM-TYP-002`): `UnitCount` (≥ 2, default 6) dwellings of `UnitWidth` 6 m through `Depth` 10 m between two end stairs of `StairWidth` 4 m: `ST1` (west), `ST2` (east), `U1…Un`. The gallery is not modelled (D-083): no gallery zone or geometry, and the gallery-side façade is an ordinary outdoor façade.
- Terrace row (`HDHM-TYP-006`): `PlotCount` (≥ 2, default 6) attached houses of `PlotWidth` 5.5 m through `Depth` 10 m, `U1…Un` named *House i*, neighbours sharing a dividing wall; one dwelling zone per plot and storey, the house's own stair not zoned; only a *Dwelling Unit* preset.
- Point plate (`HDHM-TYP-007`): a square plate of side `CoreWidth + 2 · DwellingDepth` (22 m by default) with a central core `ST` (*Core*, a `Stair` zone, 6 m square) and four dwellings `U1…U4` of `DwellingDepth` 8 m in a pinwheel around it, counter-clockwise from the south-west; every dwelling adjoins the core along one of the core's sides and has two façades; the core has no outdoor wall, the first zone of any family without one.
- Winged band (`HDHM-TYP-003`): a band of stair bays along plan x and `WingCount` (≥ 2, default 3) wings of stair bays projecting to plan north, `WingLength` 17 m long and `WingSpacing` 17 m apart, all `Depth` 12 m deep; the first wing is flush with the band's west end, the last with its east end, so the outline is a comb. Every wing adjoins the band along its whole root. The band and each wing hold `n = max(1, round(L / (2U + S)))` bays with the dwelling width adjusted to fill their length `L` (the default 70 m band has four bays of 7.25 m dwellings, the wings one bay each); stairs that leave no dwelling width are the error `InvalidParameter`. Zones `B-ST1…`, `B-U1…` (band, west to east), then `W{i}-ST1…`, `W{i}-U1…` (wing `i`, south to north). The band's north façade is fragments between the wings' roots and its bay boundaries (1.25 m to 7.25 m by default); a fragment shorter than 1 m gets no window (`WindowOmitted`, ADR-011).
- Open court (`HDHM-TYP-004`): three wings of stair bays, `Depth` 12 m deep, around a court `CourtWidth` 24 m wide and `CourtDepth` 17 m deep that is open to plan south: west and east wings of length `CourtDepth` and a north wing across the full width `2 · Depth + CourtWidth` that holds the corners. Bays are fitted to each wing as in the winged band. Zones `N-…` (west to east), then `W-…` and `E-…` (south to north); every dwelling adjoins a stair of its bay.
- Enclosed court (`HDHM-TYP-005`): four wings of stair bays, `Depth` 12 m deep, around a court `CourtWidth` 24 m wide and `CourtDepth` 24 m deep that is closed on all four sides: south and north wings across the full width `2 · Depth + CourtWidth` that hold the corners, and west and east wings of length `CourtDepth` between them. The footprint is the outer rectangle with the court as its one hole, so the court is outside the building and its façades are outdoor walls with windows, facing into it. Bays are fitted to each wing as in the winged band (by default three bays of 6.5 m dwellings in each 48 m long wing and one bay of 10.5 m dwellings in each side wing). Zones `S-…`, `N-…` (west to east), then `W-…` and `E-…` (south to north); 1728 m², 44 windows, 16 of them on the court façades.
- Office plate (`SYN-TYP-017`, S8.4): a `PlateLength` 42 m × `PlateDepth` 30 m plate with a central `CoreLength` 18 m × `CoreDepth` 6 m core `SC` (*Service Core*, a `Core` zone without outdoor walls) and one office work area `OF` (*Office*), the plate minus the core: a zone with the core as its hole in a footprint without one (D-097). The core must leave at least 3 m of work area at every façade (`OfficePlateGenerator.MinimumOfficeDepth`), or the error `InvalidParameter` names the depth left. Floor height 3.8 m; 1260 m², 4 windows.
- Cafeteria (`SYN-TYP-016`, S8.4): a `Length` 30 m plan with the kitchen and servery `KS` (`Kitchen`, `KitchenDepth` 8 m) along the whole north edge of the dining field `DI` (`Dining`, `DiningDepth` 15 m); the servery counter is the shared edge, not a zone. `KitchenDepth` must be smaller than `DiningDepth` (`InvalidParameter`). Floor height 4 m; 690 m², 6 windows.
- Hub and arms (S8.5): the radial lobes, the branching mall, the care hub, and the foyer with halls share `HubArmsLayout` (internal, `Lod.Generators/HubArms/`): a square hub with up to four arms of one width, centred on its sides in the order east, north, west, south; a family with *n* arms uses the first *n* sides (two arms east and north, three a T open to plan south, four a cross), and the bounding box's south-west corner is at the origin. Each arm has its own frame, along from the hub and across from its clockwise side, in which the families cut their zones. An arm must not be wider than the hub, and at most four arms fit the axis-aligned layout (D-100); both are `InvalidParameter`. Arms narrower than the hub leave its corners as short outdoor walls, which get no window below 1 m (`WindowOmitted`). Zones are listed hub first, then arm by arm.
- Radial lobes (`SYN-TYP-010`, S8.5): `LobeCount` (3–4, default 4) lobes, `LobeLength` 10 m and `LobeWidth` 12 m, around a `CoreWidth` 12 m core `ST` (*Core*, a `Stair` zone); each lobe holds two dwellings side by side, `L{i}-U1` (the half clockwise of the lobe's axis) and `L{i}-U2`, both adjoining the core. With three lobes the core's south side is a façade. 624 m², 16 windows.
- Branching mall (`SYN-TYP-014`, S8.5): `BranchCount` (3–4, default 3) branches from a central court as wide as the branches, `2 · ShopDepth + MallWidth` = 32 m; each branch has a `BranchLength` 40 m shop wing on either side of an 8 m mall strip, `B{i}-S1`, `B{i}-S2` (`Retail`), and an `AnchorDepth` 30 m anchor `B{i}-AN` (`Retail`) across its end. The court and every strip are one zone `MALL` (`Mall`), which every shop wing and anchor adjoins. Floor height 5 m; 7744 m², 16 windows; with four branches the mall has no outdoor wall.
- Care hub (`SYN-TYP-018`, S8.5): `WingCount` (2–4, default 3) wings of `WingLength` 30 m around a `HubWidth` 16 m communal hub `HUB` (`CareCommunal`); each wing is a `CorridorWidth` 2.4 m corridor `W{i}-CO` (`Corridor`) from the hub to the wing's end between two bedroom zones `W{i}-B1`, `W{i}-B2` (`CareBedroom`) of `BedroomDepth` 6 m. The wing width `2 · BedroomDepth + CorridorWidth` must not exceed `HubWidth`. 1552 m², 16 windows; the six 0.8 m hub corners get none (`WindowOmitted`).
- Foyer with halls (`SYN-TYP-019`, S8.5): a `FoyerWidth` 20 m foyer `FO` (`Lobby`) with `HallCount` (2–3, default 2) activity halls `H1…Hn` (`ActivityHall`) of `HallLength` 30 m × `HallWidth` 20 m and a `SupportLength` 10 m support wing `SV` (`Service`): hall 1 east, the support wing north, hall 2 west, hall 3 south; zones `FO`, `H1…Hn`, `SV`. With two halls the foyer's south side is its entrance façade. Floor height 6 m; 1800 m², 10 windows.
- Operating suite (`SYN-TYP-015`, S8.6): `SupportLength` 12 m of support rooms `SUP` (`ClinicalSupport`) across the full depth at the west end; east of them, bands of `BankLength` 36 m stacked from south to north: a dirty corridor, then per bank (`BankCount` ≥ 2, default 2) the bank of `TheatreDepth` 7 m and the next corridor, the corridors alternating dirty and clean: `DC1`, `TB1`, `CC1`, `TB2`, `DC2`, … (`DirtyCorridor` 2.4 m, `OperatingTheatre`, `CleanCorridor` 3 m). Every bank lies between one clean and one dirty corridor, no clean corridor adjoins a dirty one, and every band adjoins `SUP`. A bank's only outdoor wall is its east end, which the theatre preset's WWR 0 leaves without a window (no `WindowOmitted`). Floor height 4.2 m; 1046.4 m², 8 windows.
- Court cluster (`SYN-TYP-011`, S8.6): `CourtCount` (≥ 2, default 2) courts of `CourtWidth` 24 m × `CourtDepth` 24 m in a row along plan x, closed by wings of stair bays `Depth` 12 m deep: south and north wings across the full width `(k + 1) · Depth + k · CourtWidth`, and a west wing, `k − 1` middle wings, and an east wing between them, each middle wing bordering two courts. Bays are fitted to each wing as in the winged band (five bays of 6.9 m dwellings in each 84 m long wing by default). The footprint is the outer rectangle with one hole per court, west to east. Zones `S-…`, `N-…` (west to east), then `W-…`, `M1-…`, …, `E-…` (south to north); 2880 m², 72 windows, 16 on the façades of each court.
- Plans per storey (S8.7, D-095, [ADR-015](../decisions/ADR-015-plans-per-storey.md)): a `MultiStoreyPlanGenerator` returns one ordinary plan per storey, bottom-up, for a family whose plan differs by storey. It checks the parameters and presets once and builds every storey as `PlanGenerator` builds its plan; each plan lies at elevation 0, has the parameters' floor height and orientation, and records its storey index as the provenance parameter `Storey` (from 0) and its base elevation, the sum of the floor heights below it, as `StoreyElevation` (m, S8.8, D-108), which only the previews read (`StoreyProvenance`). A diagnostic of one storey keeps its code and subject, and its message starts with `Storey k: `.
- Stepped band (`SYN-TYP-012`, S8.7): `StoreyCount` (≥ 2, default 3) storeys of a `Length` 36 m band; on storey `k` the dwellings `U1…Un` (west to east, `n = max(1, round((Length − StairWidth) / UnitWidth))`, five of 6.4 m by default) span from `k · StepDepth` (3 m) to `BaseDepth` (14 m), beside a west stair `ST` (`StairWidth` 4 m) over the same depth, and the corridor `CO` (`CorridorWidth` 2 m) runs along the rear on every storey, adjoined by every dwelling. Each storey stands on the one below, which keeps a terrace of `Length × StepDepth` (108 m² by default), an outdoor roof once stacked (D-068); the walls facing the terraces are outdoor walls with windows. `Length` must exceed `StairWidth`, and `BaseDepth − (StoreyCount − 1) · StepDepth` must be positive (`InvalidParameter`). 576, 468, and 360 m² by default, 11 windows per storey.
- Non-residential families place one zone per department (D-097, [ADR-014](../decisions/ADR-014-program-types-and-department-zoning.md)); their default dimensions are controller design defaults (D-098). The last family of the four-source set, `SYN-TYP-012`, is built in S8.7 as the first generator of one plan per storey ([ADR-015](../decisions/ADR-015-plans-per-storey.md)); with it every family of D-093 except the set-aside `SYN-TYP-013` (D-096) has a generator, eighteen in all.
- Surfaces come from `LayoutSurfaceBuilder`: an edge shared by two zones becomes an interzone wall, an edge on the plan boundary an outdoor wall; any other edge (a gap or an overlap) is an error. The boundary includes the footprint's holes, whose edges face into the court, and every boundary edge must be covered by outdoor zone edges over its full length, so a zone placed in a court is an error too (`UnmatchedEdge`, ADR-002, S8.3). Whether a vertex lies on an edge, to split it there or to place it on the boundary, is measured between the vertices' original positions against the distance tolerance, not between their snapped grid cells, so T-junctions are recognised on rotated plans (ADR-002, S8.2). Floors and ceilings stay `Unresolved` until floors are aggregated.
- Walls carry explicit windows (position along the wall, sill, width, height; any number per wall, D-039). Every generator's rule: one centered window per outdoor wall with area = the zone preset's WWR × wall area (D-026), except on a wall shorter than 1 m or where the window would be narrower or lower than 0.3 m (`GeometryLimits`, ADR-011): that wall gets no window and the info `WindowOmitted` (subject: the wall), and the plan is produced. Every later step conserves the glazing the generator placed.
- Transform (D-070): `PlanTransform.Apply` rotates a plan about the world origin by an angle about +z (counter-clockwise seen from above, degrees) and then moves it in x and y (metres). Footprint, zones, walls, and floors and ceilings move rigidly (`PlanMotion`; whole quarter turns are exact); windows keep their offsets, sills, and sizes; IDs are kept. Wall facing follows the rotated geometry; the plan's *Orientation* (true north) is unchanged. Provenance: operation `TransformPlan`, parameters `RotationDegrees`, `TranslationX`, `TranslationY`, the source plan as input. A value that is not finite is the error `InvalidParameter`. Only plans are transformed; floors and buildings keep the geometry of their plans, and storey elevations come from the floor aggregator.

### 3. Plan simplification

| | |
| --- | --- |
| Type | `IPlanSimplifier.Simplify(IGeneratedPlan)` → `IFloor` (with `Source` and `Mapping`) |
| Components | *No Simplification* (Z0), *Semantic Merge* (Z1), *Perimeter Core* (Z2, input Depth, default 4.57 m), *Single Zone per Floor* (Z3); *Map Source to Target* lists the mapping |
| Decisions | D-019, D-034, D-038, D-039, D-041, D-047, D-079; ADR-005, ADR-007, [ADR-008](../decisions/ADR-008-perimeter-core-corners.md), [ADR-012](../decisions/ADR-012-centred-windows.md) |

- `NoSimplification` keeps the plan's zones and surfaces with an identity mapping.
- The other simplifiers share one procedure (`PlanSimplifier`). A strategy proposes target footprints; source zones are mapped to targets by overlap area (`ZoneMapping`); surfaces are rebuilt, so walls between merged sources disappear (D-034); the target outdoor walls must cover every source outdoor wall over its full length (D-041, error `FacadeNotCovered`); every source window is attributed to the target outdoor wall that contains it (`WindowRehosting`, D-039), and every target outdoor wall then gets one window centred on it with the total area of the windows attributed to it (`CentredWindows`, D-079), shaped like the generator's windows (`Window.Centered`, D-026) and none when that area is zero; a window that no single target wall contains (`WindowNotHosted`) and a wall whose glazed area is not smaller than its area (`GlazingExceedsWall`) are errors that hold by construction once the façades are covered, checked rather than repaired; programs are aggregated through the transfer fractions.
- Aggregation (ADR-005, ADR-007): each (load type, basis) component is aggregated on its own (D-047). Each source with the component transfers Tᵢ = fᵢ·Qᵢ of its design magnitude; the component's target magnitude is Q* = ΣTᵢ and its value Q*/B* in that component's basis; its schedule is s*(t) = ΣTᵢ·sᵢ(t)/Q*. Sources without the component contribute nothing to it, and mixed bases are not an error. Air-change loads are therefore volume weighted (D-019). A target is conditioned if any source contributing floor area is; its setpoints are floor-area weighted over the conditioned sources, a prescribed control rule (D-038).
- *Semantic Merge* merges connected zones of the same space type; each group's footprint is the union of its zones as tiles (`PolygonOps.UnionTiles`), which keeps the zones' own vertices and may have holes: the four dwellings of the point plate become one ring around the core (ADR-002). *Perimeter Core* makes one perimeter zone per orientation plus a core, with corners split on the bisectors (ADR-008), also at re-entrant corners; an orientation with several separate façade runs, such as the open court's three south façades, gives the zones `P-South-1…`. A footprint with holes is offset on every ring: the court façades get their own zones `P-Court-North`, `P-Court-East`, `P-Court-South`, `P-Court-West`, named by the direction they face and listed after the outer zones, and the core is a ring around the court (ADR-008, S8.3). With several courts the court trapezoids of each bin are united across the courts, giving one zone per court and bin, `P-Court-North-1`, `P-Court-North-2`, …, numbered in the union's output order, and a core with one hole per court (ADR-008, S8.6). The perimeter zones keep the footprint's own vertices, not vertices rounded to the clipping grid, so a façade edge shorter than about 1 m, such as a hub corner of the care hub, is covered by the single-zone aggregators on a rotated plan (ADR-008, S8.5). Every wing or other part of the footprint, including the wings between the outer and the court façades and between two courts, must be wider than twice the depth, or the simplifier fails with `PlanTooNarrow`, whose message says so. *Single Zone per Floor* makes the floor one zone.

### 4. Floor aggregation

| | |
| --- | --- |
| Type | `IFloorAggregator.Aggregate(IReadOnlyList<FloorEntry>)` → `IGeneratedBuilding` |
| Components | *Stack Floors*, *Stacked Floor Zone Multiplier*, *Single Zone per Floor Type*, *Single Zone Building*; inputs Floors (bottom to top) and Multipliers (optional, one per floor, whole numbers from 1, D-072, default 1) |
| Decisions | D-018, D-021, D-031, D-032, D-034, D-039, D-041, D-045, D-046, D-068, D-071, D-072, D-074, D-075, D-079; [ADR-009](../decisions/ADR-009-vertical-aggregation.md), [ADR-013](../decisions/ADR-013-vertical-aggregation-methods.md) |

All aggregators reject an empty list (`NoFloors`), multipliers below 1 (`InvalidParameter`), and floors with different orientations (`OrientationMismatch`). Floor types may have different footprints and may come from differently transformed plans.

Every aggregator first assembles the full stack (`Storeys.Assemble`, D-068): each entry repeated by its multiplier, storey `k` at the sum of the floor-to-floor heights below it, zone and surface IDs prefixed `L{k}/`. Every floor and ceiling piece is designated there: split by overlap with the zones of the storeys below and above into pieces between two storeys (`Interzone`), uncovered parts `Outdoors`, the floors of storey 0 `Ground`, and the ceilings of the top storey roofs (`Outdoors`). The footprints of each pair of adjacent storeys are clipped together as conformed polygons (`PolygonOps.Conform`, ADR-002), so the pieces keep the zones' own vertices and rotated storeys leave no zero-width slivers, spikes, or excursions. A storey `k > 0` whose floor area covered by storey `k − 1` differs from its floor area by more than the relative area tolerance gets the warning `UnsupportedStorey`, naming the storey and the uncovered area in m² (D-074); the building is still produced. The four methods differ in what they model:

| Aggregator | Storeys and zones | Multiplier Nᵢ | Floors and ceilings | Walls and windows | Internal mass |
| --- | --- | --- | --- | --- | --- |
| `Stack` | every storey of the assembly, zones `L{k}/…` | explicit repetition | as designated | as in the floors | none |
| `StackedFloorZoneMultiplier` | type `i` stands for Nᵢ storeys; a storey of a multiplied type whose floor or ceiling is ground, roof, or exposed on the stack is split off as × 1 (info `FloorTypeSplit`, D-046); each remaining group of n storeys from storey `first` is modelled by storey `first + ⌊n/2⌋` at its true elevation, zones `L{k}/…`; the other storeys are represented but not modelled (D-045) | `Zone.Multiplier = n` on every zone of the group; exposure is never multiplied; provenance parameter `Storeys`, e.g. `L0x1,L5x8,L9x1` | the modelled storeys' pieces from the stack: ground, roof, and exposed pieces kept; every piece between two storeys `Adiabatic`, whether the other storey is modelled or not (D-075) | as in the floors | none |
| `SingleZonePerFloorType` | one zone `E{i}` ("Floor type i") per floor entry, spanning its Nᵢ storeys, one part per storey outline | explicit repetition | ground, roof, and exposed pieces kept; pieces between two entries `Interzone` between `E{i}` and `E{i+1}` | rebuilt per storey outline, all outdoors, covering every source façade (D-041); one centred window per wall with the glazed area it covers (D-079); partitions discarded (D-034) | one per slab level within an entry: slab area, 2 exposed faces (D-031) |
| `SingleZoneBuilding` | one zone `BUILDING` ("Building") with one part per storey outline | explicit repetition | ground, roof, and exposed pieces kept | as `SingleZonePerFloorType` | one per slab level: slab area, 2 exposed faces (D-031) |

The single-zone methods share one merge (`SingleZoneMerge`); their storey outlines are unions of the zone footprints as tiles (`PolygonOps.UnionTiles`), so rotated plans give clean outlines whose vertices are the zones' own vertices (S8.2). An outline keeps the footprint's holes, its rebuilt walls include the court walls of every storey, and the court has no floor or ceiling piece, so it adds neither ground nor roof area (S8.3). Programs are aggregated per zone with `EquivalentPropertyAggregator` from the stacked zones (fractions 1), so every invariant is conserved; a zone is conditioned if any source is (D-038). `SingleZoneBuilding` is the former `SingleZoneMerged`, and `StackedFloorZoneMultiplier` the former `FloorAreaMultiplier` (D-071).

Storeys that differ (S8.7, [ADR-015](../decisions/ADR-015-plans-per-storey.md)): the plans of a multi-storey generator, each simplified on its own, are floor entries with multiplier 1, bottom to top, and every aggregator takes them unchanged. The part of a lower storey's ceiling that the storey above does not cover is an outdoor roof piece (a terrace), the covered part lies between the storeys; `StackedFloorZoneMultiplier` then models every storey, `SingleZonePerFloorType` makes one zone per storey, and `SingleZoneBuilding` one zone with one part per storey outline. `Building.RoofArea` counts the terraces with the top roof. A multiplier above 1 repeats a storey as for any floor and is allowed, but gives another building than the generator's.

## Grasshopper components through S8.8

All components are on the **BEMGen** tab. GUIDs never change once merged, and the GUID of a deleted component is never reused (D-064).

- **Icons (D-063).** Every component and parameter, and the plugin itself, has a 24 × 24 PNG icon: a dark glyph with one accent colour per panel (a parameter takes the colour of the panel that makes its object). `scripts/make_icons.py` (Python 3.10+, Pillow) draws them at 96 × 96, downsamples them, and writes `src/Lod.Grasshopper/Icons/<class name>.png`; it stops when a component or parameter class has no icon. The PNGs are embedded resources, loaded by `IconLibrary` by class name; a missing resource gives Grasshopper's default icon instead of an exception. S9 only polishes them.
- **Goo constructors (S9).** Every Goo has a public parameterless constructor that makes an empty, invalid wrapper. Grasshopper's `GH_Param<T>.InstantiateT` creates one with `Activator.CreateInstance` to give an empty parameter's `TypeName` (component help, the "Data conversion failed from … to …" message) and to try `CastFrom` when a wire of another type arrives (a plan into a *Floors* input). Without it the call throws and Grasshopper opens its modal *Grasshopper breakpoint* assert dialog, which blocks Rhino; the headless smoke check hung there. The parameters now report their Goo's type name (*Plan*, *Floor*, *Building*, *Program Preset*, ...), and a wrong wire ends in the conversion error. An empty wrapper is safe to use: it reads `Empty <type name>`, duplicates to another empty wrapper, casts to nothing, and has no preview (an empty clipping box).
- **Preview Location (D-062).** The eighteen plan generators, *Transform Plan*, the four plan simplifiers, and the four floor aggregators have an optional last input *Preview Location* (PL): a vector in model units, default `0,0,0` (a point converts to a vector). It moves only that component's viewport preview: the plan, floor, or building data, *Inspect*, *Validate*, and *Convert2BEM* keep the true coordinates, and downstream components do not inherit the move (each wraps its output with its own input). *Convert2BEM* has no such input. A plan or floor that is a storey of a multi-storey generator, or is made from one alone through *Transform Plan* or a simplifier, is previewed at the storey's elevation (`StoreyElevation`, S8.8, D-108) plus the *Preview Location*; every other plan and floor, and every building, is previewed at its own coordinates plus the *Preview Location*.
- **Default preset components (D-061).** *Dwelling Unit Preset*, *Corridor Preset*, and *Stair Preset*, in panel *1 Program Presets* since S8.8 (D-108) like every built-in preset component, share their inputs: Name (default the example name), WWR, Conditioned, Heating (°C), Cooling (°C), then for each load of the space type's example preset, in its order, a value input (its unit in the description: people/m², W/m², or 1/h) and an optional schedule input that replaces the built-in schedule when connected. Every input except the schedules has a default; the output is one *Preset*.
- *Example Residential Presets* (`0239f4c9-0f19-4cf1-9d90-08db878eac8a`, S2) was deleted in S4.1 (D-061); its GUID is retired.
- *Floor Area Multiplier* became *Stacked Floor Zone Multiplier* and *Single Zone Merged* became *Single Zone per Floor Type* in S4.2, keeping their GUIDs (D-064, D-071); *Single Zone Building* is new.
- **Aggregator previews (D-071, D-075).** *Stacked Floor Zone Multiplier* previews the whole stacked building: the modelled storeys as before and the storeys that are represented but not modelled in transparent grey (`StackedFloorZoneMultiplier.UnmodelledStoreys`). A zone with several parts (*Single Zone per Floor Type*, *Single Zone Building*) is previewed as one merged volume, with its windows. Only the preview changes: the building and the *Convert2BEM* outputs keep one part per storey outline.
- **Windows (S5, D-079).** No component was added or removed and no GUID changed. The descriptions of *Semantic Merge*, *Perimeter Core*, *Single Zone per Floor*, *Single Zone per Floor Type*, and *Single Zone Building* state that every rebuilt outdoor wall gets one centred window with the glazed area it covers, and the *Windows* output of *Convert2BEM* is described as one centred window per glazed outdoor wall.
- **Typology generators (S8.1, ADR-006).** *Stair Bay Bar*, *Stair Pair*, *Gallery Bar*, and *Terrace Row* follow *Linear Plan Generator*: their number inputs (counts are integers) default to the family's `Default` record, then *Floor Height* (3 m) and *Orientation* (0°), then one required preset input per space type they place (*Dwelling Unit*, and *Stair* except for *Terrace Row*; an unconnected one is Grasshopper's missing-input warning, D-065), then *Preview Location*. Their descriptions name the family and what is not modelled. `WindowOmitted` shows as a remark. *Linear Plan Generator*'s description names `HDHM-TYP-009`; its inputs and GUID are unchanged. *Point Plate*, *Winged Band*, and *Open Court* (S8.2) follow the same pattern with the preset inputs *Dwelling Unit* and *Stair*; on *Point Plate* the *Stair* preset is the core's. *Enclosed Court* (S8.3) follows the same pattern; its plan previews the court as a hole, and every zone, floor, and ceiling Brep of a footprint with holes is one face or closed extrusion with an inner loop per hole (`RhinoGeometry`). *Office Plate* and *Cafeteria* (S8.4) follow the same pattern with the preset inputs *Office* and *Core*, and *Kitchen* and *Dining*; their descriptions name the `SYN-TYP-*` family. The office work area is previewed as a ring around the core. *Radial Lobes*, *Branching Mall*, *Care Hub*, and *Foyer Halls* (S8.5) follow the same pattern, their count input (*Lobe Count*, *Branch Count*, *Wing Count*, *Hall Count*) an integer first, with the preset inputs *Dwelling Unit* and *Stair* (the core's); *Mall* and *Retail*; *Care Bedroom*, *Care Communal*, and *Corridor*; and *Lobby*, *Activity Hall*, and *Service*. *Operating Suite* and *Court Cluster* (S8.6) follow the same pattern, their count input (*Bank Count*, *Court Count*) an integer first, with the preset inputs *Operating Theatre*, *Clean Corridor*, *Dirty Corridor*, and *Clinical Support*, and *Dwelling Unit* and *Stair*; the court cluster's plan previews every court as a hole. *Stepped Band* (S8.7) follows the same pattern, its *Storey Count* an integer first, with the preset inputs *Dwelling Unit*, *Corridor*, and *Stair*; its *Plan* output is a list, one plan per storey bottom-up (ADR-015), and each storey is previewed at its elevation (the floor heights below it) on top of the *Preview Location*, while the plans keep elevation 0.
- **Wiring storeys that differ (S8.7, ADR-015).** Connect the *Stepped Band*'s *Plan* list to a plan simplifier (optionally through *Transform Plan*); Grasshopper runs it once per storey, and its *Floor* output is the list of floors in the same order. Connect that list to a floor aggregator's *Floors* and leave *Multipliers* unconnected: every storey counts once, bottom to top. *Transform Plan* and every simplifier preview each storey's plan or floor at the storey's elevation, as the generator does (S8.8, D-108; through S8.7 they previewed it at 0), each plus its own *Preview Location*; the data stay at elevation 0, and the aggregator places the storeys. A *Single Zone Building* or *Single Zone per Floor Type* zone whose storey outlines differ is previewed by a boolean union of its storeys, as for setbacks (`RhinoGeometry.MergedZoneBreps`).
- **Default preset components of the non-residential types (S8.4, ADR-014).** *Office Preset* to *Service Preset* share the inputs of the residential ones (above), one value and one optional schedule input per load of their example preset; *Gas Equipment* is in W/m², *Ventilation* and *Infiltration* in 1/h. Zones of the new types have their own preview colours.
- **Any Program Preset (S8.8, D-108).** A floating parameter in panel *1 Program*, like Grasshopper's *Geometry* parameter: place it on the canvas, wire a preset into its left grip (any default preset component, *Program Preset*, or another preset parameter), and wire its right grip into any preset input of any plan generator. It outputs each preset as an any-program preset (`AnyProgramPresetGoo`, shown as `Preset <name> (any program, no space type, WWR <ratio>)`), with the same name, program, and WWR; it holds no data of its own, so an unconnected one is empty. The generator's preset inputs take it (`ProgramPresetParameter` converts it), and their descriptions say so in one shared text. The zones keep the input's space type (preview colour, *Semantic Merge* groups, *Convert2BEM* *Space Types*) and take the preset's program; *Inspect*'s provenance shows `AnyProgramPreset.<Input>`. A preset wired directly, without the parameter, must still have the input's space type.
- **Panels (S8.8, D-108).** *1 Program* holds *Schedule*, *Load*, *Program Preset*, and *Any Program Preset*; the eighteen built-in preset components are in *1 Program Presets*, next to it. Their icons keep the *Program* accent. No GUID changed.
- **Enum inputs (D-120).** The inputs that take the name of an enum value, *Schedule* *Kind* (`ScheduleKind`, default `Fraction`) and *First Day* (`DayOfWeek`, default `Monday`), *Load* *Type* (`LoadType`) and *Basis* (`LoadBasis`), and *Program Preset* *Space Type* (`SpaceType`), are text inputs of the internal class `EnumParameter<TEnum>`, a `Param_String`. Text from a panel or wire works as before and is parsed ignoring case; a name that is not a value is an error listing the valid names. Right-click the input to choose a value: the names follow *Manage Text collection*, the current one ticked, and are disabled while the input has a source. *Extract parameter* places a *Value List* in dropdown mode left of the input, labelled with its name, with every name in declaration order (each outputs its name as text), selected on the current value (the first name when the value is not one), and wired into the input; it moves down past any object it would overlap, such as the dropdown of the input above, and adding it and the wire are one undo step. The class is internal and generic, so Grasshopper never registers it. It keeps the *Text* parameter's `ComponentGuid` and icon, so a saved definition records the input as a Text parameter; it must not get a GUID of its own. No component GUID, input name, nickname, access, or default changed.
- **Transform Plan (D-070).** Its *Transform* input is a Grasshopper transform in model units. The component applies the rotation about the world z axis, `atan2(M10, M00)`, and the x-y translation (`M03`, `M13`) converted to metres with the preview's unit scale (`PlanMotionDecomposition`). A translation along z, a plan part that is not a pure rotation (scaling, shear, mirroring), a rotation about another axis or scaling along z, and a projection are not applied; they are named in one warning, `Not applied (D-070): …. Applied: a rotation of …° about the world z axis and a translation of (…, …) m in x and y.` Matrix entries are compared within `ToleranceSettings.Angle`, the z translation within `Distance`.
